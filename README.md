## v0.6 — 조용히 실패하던 수집 파이프라인 (현행)

일지 시스템에서 가장 위험한 실패는 "일지가 안 써진다"가 아니라 **"빠뜨린 채로 써진다"**입니다.
수집이 0건이어도 등록은 성공으로 끝나고, 44건 중 5건만 도달해도 응답은 정상으로 나옵니다.
사용자에게는 "그날 한 일이 이게 전부"로 읽힙니다. 이 구간에서 그런 경로 여섯 개를 막았습니다.

```
"2026-07-28 일지 써줘"

before  44건이 저장돼 있는데 5건만 도달 — 39건(89%)이 에러도 경고도 없이 사라짐
        남은 5건은 "중요한 5건"이 아니라 "먼저 저장된 5건"
after   44건 전부 도달. 예산을 넘기면 제외 건수와 담긴 기간을 응답에 명시
```

- **`if not repo_dir.exists(): clone(...)` 에 `else`가 없었다** — 이미 받아둔 저장소는 **한
  번도 갱신되지 않았다.** 에러도 경고도 없이 clone 이후의 커밋이 영원히 수집되지 않는다.
  `_sync_repo`로 통합한 뒤, 회귀 테스트를 붙이고 **수정 전 코드로 되돌려 5건이 FAIL하는 것을
  확인**해 테스트의 실효성을 검증했다.

- **검색이 `limit=5`로 조용히 잘렸다** — 원인이 셋 겹쳐 있었다. LLM이 `reference_len`을 임의로
  5로 잡았고, 날짜 필터는 정확일치라 문서 사이에 우열이 없어 순위가 무의미했고, 그래서 남는
  것이 **먼저 저장된 5건**이었다. 나중에 임베딩한 소스가 통째로 밀려난다. → `reference_len`
  제거, 글자 예산 도입, **제외 건수와 담긴 기간 명시.**

- **커밋 1건 = 문서 1개가 부피의 82%를 메타데이터로 채우고 있었다** — 커밋 67건 14,221자 중
  53%가 파일 변경 목록, 29%가 날짜+작성자 반복. 하루당 문서 1개로 묶어 **67개 → 8개(69%↓).**
  검증은 sha 대조로 했다 — 원본 67건에서 merge 2건·빈 커밋 1건을 뺀 64개가 저장분과 완전 일치.

- **빈 문서를 저장하면서 유실은 세지 않았다** — merge 커밋은 `git log --numstat`이 아무것도
  내보내지 않아 텅 빈 문서가 저장됐고, 제외 건수를 세는 코드가 없어 **유실이 통계에 안
  잡혔다.** 둘이 맞물려 "빠진 게 없어 보이는" 상태를 만든다. → `skip_reasons`에 사유별 기록.

- **일지의 「막힌 것 / 예정」이 늘 비어 있었다** — 커밋과 문서에는 그 정보가 없다. Claude Code
  트랜스크립트 12세션 19MB 중 **사람이 실제로 친 말은 179건 17KB(1%)**뿐이었다(약 567:1).
  그 1%만 뽑는 수집기를 붙였다.

- **모델은 `user_id`를 한 번도 빠뜨리지 않았다** — 최초 진단은 "모델이 자꾸 빠뜨린다"였고
  스키마에서 숨기는 방안까지 설계했다. LangSmith로 실측하니 **스크립트 직접 호출 14건이 전부,
  에이전트 경유 23건은 0건**이었다. 진짜 원인은 시그니처 변경을 따라가지 못한 낡은 테스트
  코드. → 계약 테스트로 스키마 수준에서 못 박았다.
  **실패 건수만으로 원인을 귀속하면 안 된다. 어느 경로에서 났는지를 갈라야 한다.**

- **assert 0개 · except 8개짜리 테스트가 항상 통과하고 있었다** — 무엇이 깨져도 통과하면서
  실제 LLM을 호출하고 사용자 데이터를 오염시켰다. 위 `user_id` 사건이 오래 안 잡힌 이유다.
  → pytest 수집 범위를 `tests/`로 제한. 실행 시간 49.7s → **19.1s**, LLM 호출 5회 → **0회**.

- **조회 결과가 대화에 눌러앉아 매 호출마다 재전송됐다** — 조회 결과 10,321토큰이
  `InMemorySaver`에 남았다. 같은 thread 5회에 275,265토큰($0.83) vs 새 대화마다
  63,285토큰($0.19). 실측에서 나온 비직관적 결론: **스레드 분리와 프롬프트 캐싱은 보완재가
  아니라 대체재다**(분리하면 매번 새 도구 결과라 캐시 효율이 12%로 떨어진다).
  → 저장 직전 도구 트래픽 제거 + 프롬프트 접두부 캐싱. 요청당 새로 과금되는 토큰
  **11,742 → 531.**

- **git log 명령을 세 번에 걸쳐 줄였다** — `--numstat` → `--name-only` → (`--graph` 제안은
  실측으로 반박) → `--filter=blob:none --no-checkout`. 커밋 메타데이터만 읽으므로 파일 본문을
  아예 받지 않는다. **756K → 168K (78%↓).**

### + v0.5 — 일지 품질을 측정할 수 있게 만들다

**문제는 재는 대상이 아니라 자[尺]에서 나왔다.** 평가 지표를 먼저 고쳐야 모델 비교가
가능했습니다.

- **분모가 0이라 자동 만점이 나오고 있었다** — `hits / len(blockers) if blockers else 1.0`.
  정규식으로 뽑은 분모가 **55일 중 43일(78%)에서 0개**였다. 94~98%라는 점수의 대부분이 채점
  결과가 아니라 자동 만점이었다
- **LLM에게 매번 물으면 재현되지 않는다** — 같은 자료로 3번 돌려 6개·10개·8개. 일지를 고치지
  않아도 점수가 30%p씩 움직인다. → TREC 풀링 방식으로 **분모를 한 번만 만들어 파일로 고정.**
  LLM 호출 165회 → **0회**, 사람이 파일을 열어 오탐을 지울 수 있다
- **그래서 결론이 뒤집혔다** — 분모 고치기 전 "세 모델 차이 최대 3.7%p, 무의미하다" → 고정 후
  Haiku 60.3% / Sonnet 68.0% / **Opus 75.7%(15.4%p)**. **불완전한 분모가 "차이 없음"이라는
  거짓 결론을 만들어냈다**
- **그런데 Opus를 쓰지 않기로 했다** — Opus의 우위가 **오탐 의심 구간에서 가장 크다(+19.4%p)**.
  Sonnet 5는 확실한 항목에서 Opus의 98% 수준을 내면서 의심스러운 항목은 16%p 덜 집는다
- **길이를 점수화해 비대칭이 생겼다** — `concise = min(1.0, 500/length)`. Opus가 890자를 쓴
  것은 더 많이 찾아냈기 때문인데, 추가로 잡은 항목은 분모에 없어 반영되지 않고 길이만 정확히
  측정돼 감점됐다. **측정 가능한 것만 벌하는 구조였다.** → 길이 점수 삭제, 프롬프트의 500자
  제한도 폐지

**모델을 바꾸지 않고 프롬프트만 고쳐 커밋 반영 98%→100%, 막힌 것 포착 90%→96%를 얻었습니다.**
나중에 모델을 올려서 얻은 것은 비용 5배에 1~4%p였습니다.

## 왜 만들었나

개발 기록은 이미 여기저기 쌓여 있습니다. Git 커밋, TIL 마크다운, AI와 나눈 대화. 문제는 그게
**날짜로 검색되지 않는다**는 것입니다. "지난주 화요일에 뭐 했더라"를 알려면 커밋 로그를 훑고,
옵시디언을 뒤지고, 대화 기록을 스크롤해야 합니다.

이 프로젝트는 그 세 갈래를 날짜 메타데이터와 함께 한 벡터DB에 넣고, 날짜로 뽑아 그날의 일지를
쓰게 합니다. 일지 자체가 압축 계층이 되므로, 나중에는 원문 대신 일지를 검색하면 됩니다.

```
원문(문서 · 커밋 · 대화)  →  그날의 일지  →  위키 / 개념 노드
   수백 MB                    하루 몇 KB       (미착수)
```

## 🏗️ 아키텍처

```
사용자 → 웹 UI (로그인 / 개인페이지 / 설정) → FastAPI (src/router.py)
                                                   ↓ POST /unified_agent
                                    LangGraph 단일 Agent (Claude Sonnet 5)
                                                   ↓ 도구 9개
        ┌──────────────────────┬──────────────────────┬──────────────────────┐
        │  소스 CRUD           │  임베딩 실행/상태     │  날짜 검색 + 일지    │
        │  src/tools/source.py │  src/tools/embedding │  src/tools/log.py    │
        └──────────────────────┴──────────────────────┴──────────────────────┘
                                                   ↓
              SQLite (사용자 · 소스 메타데이터) · ChromaDB (사용자별 컬렉션)
```

**수집 소스 3종** — git 파일(`.md`/`.txt`), git 커밋 로그(하루 1문서로 묶음),
Claude Code 대화 로그(사람 발화만 추출). 전부 `date` 메타데이터를 `YYYY-MM-DD`로 통일해
기록하고, **날짜를 끝내 추출할 수 없는 파일은 수집하지 않습니다.**

세부 컴포넌트와 데이터 흐름은 [docs/ARCHITECTURE.md](docs/ARCHITECTURE.md) 참고.

### `SHRINK_STEPS` 축약 — 고치지 않기로 한 것

`src/tools/log.py:43`의 `SHRINK_STEPS = (3, 0)`은 v0.6의 커밋 날짜 묶기 이후 의도대로
동작하지 않습니다. `- `로 시작하는 줄을 지우는 코드인데, 예전엔 그게 파일 경로였고 지금은
**커밋 메시지 본문**입니다. `keep=0` 단계에서는 "외 N개"도 안 붙고 내용이 통째로 사라집니다.

**그런데 주 경로가 이 로직을 타지 않습니다.** 일지 생성은 `generate_daily_journals`가 기간을
날짜별로 쪼개 순회하므로 하루치가 예산을 넘길 일이 없습니다. 남는 노출은 Agent가
`retriever_vectordb`를 기간으로 직접 호출하는 경우 하나뿐이고, 그 경로는 일지 생성의 주
흐름이 아닙니다.

**고치지 않기로 했습니다.** 실사용 경로가 우회하는 문제에 축약 로직 재설계(개명 포함 Task
6개)를 넣는 것보다, 같은 시간을 아직 손대지 않은 항목에 쓰는 편이 낫다고 봤습니다.

남아 있는 것은 유실 자체보다 **유실을 알리지 않는다는 점**입니다 — 직접 호출 경로에서 내용이
날아가면 안내문은 여전히 "커밋의 파일 변경 목록을 생략했습니다"라고 나가는데, 실제로 지운 것은
내용 전부라 **사실과 다릅니다.** 이 경로에 부딪히면 그때 손볼 예정입니다.

| 삭제한 파일의 청크가 남음 | 재동기화 시 *다시 넣는* 문서만 정리하므로 삭제분은 영원히 남음 |
| `InMemorySaver` | 재시작하면 대화가 사라지고, 워커를 늘리면 워커별로 기억이 갈림 |
| memsearch 수집기 | 미구현 (`[], {}` 반환) |
| 작성자 필터 | 연기 — 팀 저장소에서 남의 커밋이 섞일 수 있음 |
| CI 테스트 게이트 | 없음 — 빌드→배포만 하고 `pytest`를 돌리지 않음 |
| `docs/ARCHITECTURE.md`의 「알려진 이슈」 | 낡음 — 거기 적힌 `/sync_git_repo`·`/call_agent`는 v0.4에서 이미 제거됐다 |
| `check_embeddings.py` | 깨짐 — 메타데이터 키가 수집기와 불일치 |

전체 목록과 원인은 [CHANGELOG.md의 「알려진 한계」](CHANGELOG.md#알려진-한계) 참고.
