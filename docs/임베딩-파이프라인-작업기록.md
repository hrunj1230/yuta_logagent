## 📋 이 문서의 성격

`임베딩-파이프라인-문제분석.md` 가 **무엇이 문제였고 어떻게 되었는가**를 다룬다면,
이 문서는 **어떻게 그 결론에 도달했는가**를 다룬다.

같은 종류의 문제를 다시 마주쳤을 때 재현할 수 있는 절차로 남기는 것이 목적이다.

## 1. 출발점 — 잘못된 질문에서 시작했다

처음 논의는 이렇게 시작했다.

> "로컬 문서나 Git 작업 내용, AI 채팅 내용을 저장하면 양이 너무 많을 것 같고,
> 저장하지 않으면 매번 임베딩해야 해서 속도나 효율이 안 좋을 것 같다."

이것은 **저장 용량에 대한 설계 질문**이었다. 그러나 실제로 측정해 보니 전제가 성립하지 않았다.

### 측정한 것

| 항목 | 실측값 |
|---|---|
| `data/sources` 원문 | 4.8 MB / 105개 파일 |
| ChromaDB 내 실제 텍스트 | 901 KB |
| `chroma.sqlite3` | 12 MB |
| 벡터 실체 (`data_level0.bin`) | 320 KB |
| `~/.claude/projects` (AI 대화 로그) | 52 MB / 79 세션 |

### 여기서 나온 두 가지 판단

1. **문서와 Git은 볼륨 문제가 아니다.** 연간 수십 MB 규모다. 볼륨이 문제가 되는 소스는 AI 대화 로그 하나뿐이다.
2. **원문 901KB인데 DB가 12MB인 것이 이상하다.** 13배는 오버헤드로 설명되지 않는다.

두 번째 이상 신호를 파고든 것이 이번 작업의 실질적인 출발점이 되었다.

> **교훈:** 설계 질문을 받았을 때 바로 설계를 논하지 말고 먼저 측정한다.
> 측정값이 전제와 어긋나면, 그 어긋남 자체가 진짜 문제의 위치를 알려준다.

## 2. 증거 수집 — 코드를 읽기 전에 데이터를 봤다

원인을 추측하는 대신 ChromaDB의 SQLite를 직접 조회했다.

**파일별 청크 수 집계:**

```sql
select m.string_value, count(*)
from embedding_metadata m
where m.key = 'file_path'
group by 1 order by 2 desc
```

결과: 상위 3개가 `.obsidian/plugins/*/main.js` 이고 합계 510개.
전체 572개 중 **89%** 였다.

**메타데이터 키 목록 조회:**

```sql
select key, count(*) from embedding_metadata group by key order by 2 desc
```

결과에 `date` 키가 없었다. `embedded_at` 값은 전부 `2026-07-29T00:47:34` 로 동일했다 —
문서 날짜가 아니라 임베딩을 실행한 시각이었다.

> **교훈:** "왜 검색이 이상하지?"를 코드에서 찾기 전에 **저장된 데이터를 먼저 본다.**
> 데이터는 코드가 실제로 무엇을 했는지에 대한 증거다. 코드는 의도만 보여준다.

## 3. 원인 사슬을 연결했다

데이터에서 확인한 두 사실을 코드와 대조하니 세 문제가 하나로 이어졌다.

```
P2  embedding.py가 date 메타데이터를 안 만듦
     │
     └→ P3  log.py가 where={"date": ...}로 조회 → 항상 빈 결과
              │
              └→ 조용히 similarity_search("작성 날짜: 2026-08-01")로 폴백
                   │
                   └→ P1  코퍼스 89%가 플러그인 JS → 자바스크립트가 반환됨
```

핵심 인식은 **"날짜 검색이 부정확한 게 아니라 처음부터 동작한 적이 없다"** 는 것이었다.

폴백이 `print("[DEBUG] ...")` 로만 기록되어 호출자에게 전달되지 않았기 때문에,
실패가 "그럭저럭 동작하는 것처럼" 보였다.

> **교훈:** 조용한 폴백은 버그를 감춘다.
> 폴백이 원래 의도와 무관한 동작이라면(날짜 필터 → 날짜 문자열 유사도 검색),
> 그것은 폴백이 아니라 **실패를 숨기는 코드**다.

## 4. 결정이 필요한 지점에서 멈췄다

수정을 시작하기 전에 두 가지를 사용자에게 물었다.

| 질문 | 결정 |
|---|---|
| 코드 프로젝트에서 무엇을 수집할 것인가 | 커밋 로그 + diff 요약 |
| 기존 벡터DB를 어떻게 할 것인가 | 전체 삭제 후 재임베딩 |

**diff 수집 방식은 결정을 그대로 따르되 구현에서 보완했다.**
raw diff 본문(`+`/`-` 라인)은 임베딩 품질이 낮고 볼륨이 크다는 문제가 있어,
`git log --numstat` 기반의 구조화 요약으로 대체했다.

```
[2026-07-30] fix: prune old tagged images after deploy to prevent disk exhaustion
작성자: hrunj1230
변경: 2개 파일 (+22 / -3)
- docs/cicd-setup.md (+18/-1)
- scripts/deploy.sh (+4/-2)
```

이 형태는 사용자가 요청한 정보량(어떤 파일이 얼마나 바뀌었는가)을 유지하면서
diff 원문의 단점을 피한다.

> **교훈:** 사용자 결정의 *의도*를 만족시키되, 구현 수준의 함정은 개발자가 막는다.
> 결정을 무시하는 것과, 결정을 더 나은 형태로 실현하는 것은 다르다.

## 5. 순수 함수로 분리하고 테스트를 먼저 썼다

수정 대상인 `embedding.py` 는 이미 437줄로 수집·필터·날짜·청킹·저장을 모두 하고 있었다.
여기에 필터와 날짜 로직을 더 넣으면 테스트가 불가능해진다.

그래서 **외부 의존성이 없는 순수 함수만 별도 모듈로 분리**했다.

`src/tools/ingest_rules.py`:
- `should_collect(path, root)` — 확장자 / 제외 디렉토리 / 크기 판정
- `normalize_date(raw)` — 다양한 표기를 `YYYY-MM-DD` 로
- `parse_user_date(raw)` — 사용자 입력용 관대한 파서
- `date_from_filename`, `date_from_frontmatter`, `git_file_dates`, `resolve_date`

ChromaDB도, 임베딩 모델도, 네트워크도 필요 없다. 그래서 테스트가 **0.2초**에 끝난다.

```
uv run pytest tests/unit/test_ingest_rules.py -q
48 passed in 0.22s
```

> **교훈:** 판단 로직(무엇을 수집할지, 어떤 날짜를 붙일지)과
> 부수효과(파일 읽기, DB 저장)를 분리하면 판단 로직은 전부 테스트할 수 있다.
> 임베딩 모델 로딩에 30초가 걸리는 파이프라인에서 이 분리는 특히 값이 크다.

## 6. 드라이런으로 실데이터에 먼저 돌렸다

임베딩을 실행하기 전에, **필터와 날짜 추출만** 실제 TIL 저장소에 돌려 결과를 확인했다.

**1차 드라이런 결과:**

```
수집 대상: 35개   날짜 출처: {'git': 8, 'filename': 27}
제외: {'excluded_dir:.git': 28, 'no_date': 24, 'excluded_dir:.obsidian': 17, ...}
```

`no_date: 24` 가 이상했다. git 날짜 매핑에는 109개 경로가 있는데 24개가 날짜를 못 받았다.

### 여기서 P8을 발견했다

한글 파일명이 원인일 것으로 보고 git 출력을 직접 확인했다.

```console
$ git log --pretty=format:__C__%ad --date=short --name-only | grep -m3 '회'
"AI\355\201\264\353\235\274\354\232\260\353\223\234 ... .md"
"\353\251\230\355\206\240\353\247\201--22.md"

$ git -c core.quotepath=false log ... | grep -m3 '회고'
회고록/week07 회고록.md
회고록/week05 회고록.md
```

**git은 기본 설정에서 비ASCII 경로를 8진수로 이스케이프한다.**
그래서 날짜 매핑의 키가 실제 파일 경로와 매칭되지 않았다.

`git -c core.quotepath=false` 로 두 곳(`git_file_dates`, `_collect_git_log`)을 수정하고
회귀 방지 테스트를 추가했다.

**2차 드라이런 결과:**

```
수집 대상: 59개   날짜 출처: {'git': 32, 'filename': 27}
제외: {'excluded_dir:.git': 28, 'excluded_dir:.obsidian': 17, 'extension:none': 1}
```

`no_date` 가 0이 되었고, 수집 대상이 저장소의 `.md` 파일 수(59개)와 정확히 일치했다.

> **교훈:** 비용이 큰 단계(임베딩)를 실행하기 전에,
> 비용이 없는 단계(필터·파싱)만 실데이터에 돌려 본다.
> 이 드라이런이 없었다면 P8은 "한글 문서가 왠지 검색이 잘 안 되네" 로 오래 남았을 것이다.

## 7. 재구축을 일회성 명령이 아니라 스크립트로 만들었다

수집 규칙이나 날짜 로직이 바뀌면 재인덱싱이 다시 필요해진다.
그래서 `scripts/reindex.py` 로 남겼다.

절차: **백업 → 컬렉션 삭제 → 등록된 소스 전체 재임베딩**

```console
$ uv run python -m scripts.reindex hrunj1230
💾 백업 완료: backups/chroma_db.backup_20260802_195703
🗑️  기존 컬렉션 삭제 중...
✅ 임베딩 완료: Yuta_TIL
- 수집된 문서: 59개
- 생성된 청크: 62개
- 제외된 파일: 48개
```

원문은 `data/sources` 와 원격 저장소에 그대로 있으므로 복구 위험이 없지만,
그래도 삭제 전에 `backups/` 로 복사하도록 했다.

### 이 과정에서 발견한 것

`users.db` 의 `users` / `sources` 테이블이 **비어 있었다.**
기존 572개 청크는 등록이 이미 삭제된 소스의 잔재였다.

재구축하면서 두 소스를 다시 등록했다.

| ID | 이름 | 타입 |
|---|---|---|
| 1 | Yuta_TIL | `git` (문서 본문) |
| 2 | yuta_logagent 커밋이력 | `git_log` (커밋 + 변경 요약) |

옛 `user_id` 시절의 잔재 컬렉션 `user_hrun` 도 함께 삭제했다.

> **교훈:** 파괴적 작업은 스크립트로 만든다.
> 한 번 쓰고 버릴 명령처럼 보여도, 규칙이 바뀌면 반드시 다시 필요해진다.
> 스크립트로 만들면 백업 단계를 빠뜨릴 수 없게 된다.

## 8. 시나리오로 검증했다

단위 테스트는 순수 함수만 덮는다. 실제 동작은 도구를 직접 호출해 확인했다.

| 시나리오 | 결과 |
|---|---|
| 기록이 있는 날짜 (`2026-07-22`) | ✅ 해당 날짜 문서만 반환 |
| 기록이 없는 날짜 (`2026-01-05`) | ✅ 명시적 안내 + 기록이 있는 날짜 목록 |
| 기간 조회 (`2026-07-20` ~ `2026-07-24`) | ✅ 범위 내 문서 반환 |
| 한국어 날짜 (`2026년 07월 21일`) | ❌ → 수정 후 ✅ |
| 커밋 이력 (`2026-07-30`) | ✅ 변경 파일·증감량 포함 |
| 일지 저장 → 즉시 검색 | ✅ 검색 결과에 포함 |
| 같은 날짜 일지 재저장 | ✅ 이전 일지 교체 |

### 검증 중 추가로 고친 것

한국어 날짜(`2026년 07월 21일`)가 해석되지 않았다.
도구의 docstring에는 지원한다고 적혀 있었고, 수정 전 코드는 `re.sub(r'\D','',date)` 로
모든 비숫자를 제거해 이 표기를 처리하고 있었다.

새로 만든 `normalize_date` 는 파일명 파싱용이라 엄격했다. 여기에 관대한 규칙을 넣으면
`week03 과제.md` 같은 파일명에서 오탐이 날 수 있다.

그래서 **경로를 나눴다.**

- `normalize_date` — 파일명·메타데이터용. 엄격하게 유지
- `parse_user_date` — 사용자 입력용. 한글 구분자, 한 자리 월/일, 연도 생략 허용

> **교훈:** 같은 "날짜 파싱"이라도 **신뢰할 수 없는 입력(사용자)** 과
> **구조가 정해진 입력(파일명)** 은 다른 함수여야 한다.
> 하나로 합치면 한쪽의 관대함이 다른 쪽의 오탐이 된다.
