# 일지 생성 모델 비교 기록 (Haiku · Sonnet · Opus)

**작성일:** 2026-08-03
**대상:** Claude Haiku 4.5 / Sonnet 5 / Opus 5
**데이터:** alex · 55일 · 272청크 (문서 126 + 커밋 91 + 대화 55)
**결정:** **Sonnet 5 채택, 길이 제한 폐지**

---

## 📋 요약

세 모델에 같은 자료와 같은 프롬프트를 주고 55일치 일지를 생성해 비교했다.
처음 측정에서는 세 모델의 차이가 3.7%p로 "유의미하지 않다"는 결론이 나왔으나,
**그것은 측정 도구의 결함이었다.** 분모를 바로잡자 격차는 15.4%p로 벌어졌다.

| 모델 | 커밋 반영 | 막힌 것 포착 | 환각 없음 | 평균 길이 |
|---|---|---|---|---|
| Haiku 4.5 | 97.3% | 60.3% | 97.3% | 567자 |
| **Sonnet 5** | **99.1%** | **68.0%** | 96.6% | 618자 |
| Opus 5 | 97.3% | **75.7%** | **97.4%** | 890자 |

Opus가 막힌 것 포착에서 가장 높지만, 뒤에서 보듯 그 우위의 상당 부분이
잡음과 중복에서 온다. **Sonnet을 채택했다.**

## 1. 측정 도구를 먼저 고쳐야 했다

### 1.1 처음 지표의 결함

「막힌 것 포착」의 분모를 정규식으로 셌다.

```python
_BLOCKER = re.compile(r"\?{2,}|헛점|허점|매끄럽지|모르겠|불명확|헷갈")
```

`???`나 "헛점" 같은 **표시가 붙은 것만** 세므로, 55일 중 43일(78%)에서 분모가 0이었다.
분모가 0이면 코드가 자동으로 100점을 준다 — 잡을 것이 없으니 놓친 것도 없다는 논리다.

그 결과 "막힌 것 포착 94~98%"라는 높은 점수는 **대부분 자동 만점에서 나온 값**이었고,
모델 간 차이가 드러날 자리가 없었다.

### 1.2 LLM에게 매번 묻는 방식은 재현되지 않는다

정규식 대신 LLM에게 분모를 물으면 정확해지지만, 같은 자료·같은 프롬프트·같은 모델로
세 번 돌린 결과가 이렇게 나온다.

| 실행 | 추출된 항목 수 |
|---|---|
| 1회차 | 8개 |
| 2회차 | 10개 |
| 3회차 | 6개 |

분모가 6~10 사이에서 흔들리면, 일지를 한 글자도 고치지 않아도 점수가 달라진다.
같은 일지가 5개를 잡았을 때 분모 6이면 83%, 분모 10이면 50%다.

**33%p 차이가 순전히 채점자의 변덕에서 나온다.** 이러면 프롬프트 개선이 진짜인지
노이즈인지 구분할 수 없고, 모델 간 3.7%p 차이는 아무 의미가 없다.

> 참고: Sonnet 5와 Opus 5는 `temperature` 파라미터가 제거되어 400 에러를 반환한다.
> 최신 모델에서는 결정론을 **요청할 수단조차 없다**.

### 1.3 해법 — 분모를 한 번 만들어 고정한다

`scripts/build_blocker_pool.py`

| 단계 | 방법 | 비용 |
|---|---|---|
| 추출 | 세 모델이 각자 원자료에서 막힌 지점을 뽑음 | 55일 × 3모델, **1회** |
| 병합 | 로컬 임베딩 코사인 유사도 ≥ 0.60 이면 같은 항목 | 0 (로컬 모델) |
| 저장 | 날짜별 `<date>.blockers.json` | — |
| 채점 | 파일을 읽어 대조 | **0** |

여러 모델의 결과를 합집합으로 모으는 이유는 정보검색 평가의 **풀링(pooling)** 과 같다.
한 모델이 만든 목록으로 채점하면 그 모델의 관점이 곧 정답이 되어 자기 자신에게 유리해진다.

병합 임계값 0.60은 실측으로 정했다.

| 쌍 | 유사도 | 합쳐야 하나 |
|---|---|---|
| "느린 코랩" ↔ "코랩이 느려서 불편함" | 0.770 | 예 |
| "왜 이렇게 복잡하지?" ↔ "이미 다 한 걸 왜 복잡하게 하나" | 0.638 | 예 |
| "랭체인 없이도…" ↔ "랭그래프 없이도…" | 0.802 | 예 |
| "새로운 개념 쏟아짐" ↔ "성과의 정량 지표화" | 0.117 | 아니오 |
| "느린 코랩" ↔ "코드 검증 근거?" | 0.275 | 아니오 |

합쳐야 할 쌍(0.638~0.802)과 아닌 쌍(0.117~0.275) 사이가 넓게 비어 있어 경계가 명확하다.

### 1.4 고친 결과

| | 이전 (정규식) | 이후 (고정 풀) |
|---|---|---|
| 분모 합계 | 12개 | **300개** |
| 분모 0인 날 | 43일 (78%) | 0일 |
| 재현성 | 완벽 | 완벽 |

같은 Haiku 일지의 점수가 **96% → 58%** 로 바뀌었다. 38%p가 측정 착시였다.

## 2. 모델 비교 결과

### 2.1 전체

**min_support=1** (분모 300개 — 한 모델이라도 찾은 항목 전부)

| 모델 | 커밋 반영 | 막힌 것 포착 | 환각 없음 | 길이 |
|---|---|---|---|---|
| Haiku 4.5 | 97.3% | 60.3% | 97.3% | 567자 |
| Sonnet 5 | 99.1% | 68.0% | 96.6% | 618자 |
| Opus 5 | 97.3% | 75.7% | 97.4% | 890자 |

**min_support=2** (분모 125개 — 2개 이상 모델이 합의한 항목만)

| 모델 | 커밋 반영 | 막힌 것 포착 | 환각 없음 | 길이 |
|---|---|---|---|---|
| Haiku 4.5 | 97.3% | 75.3% | 97.3% | 567자 |
| Sonnet 5 | 99.1% | 80.8% | 96.6% | 618자 |
| Opus 5 | 97.3% | 85.9% | 97.4% | 890자 |

두 기준에서 순위와 격차의 방향이 같다.

### 2.2 합의 수준별 — 우위가 어디서 오는가

이것이 판정의 근거다. 3/3 합의 항목은 진짜일 가능성이 높고, 1/3 단독 항목은
오탐일 가능성이 높다.

| support | 항목수 | Haiku | Sonnet | Opus | Opus−Haiku |
|---|---|---|---|---|---|
| **3/3** (확실) | 57 | 70.2% | 80.7% | 82.5% | +12.3%p |
| **2/3** | 68 | 66.2% | 72.1% | 80.9% | +14.7%p |
| **1/3** (의심) | 175 | 50.9% | 54.3% | 70.3% | **+19.4%p** |

**Opus의 우위가 오탐 의심 구간에서 가장 크다.**

Sonnet의 위치를 보면 더 분명하다.

```
3/3 확실 구간   Haiku 70.2% → Sonnet 80.7% → Opus 82.5%
                        +10.5%p        +1.8%p

1/3 의심 구간   Haiku 50.9% → Sonnet 54.3% → Opus 70.3%
                         +3.4%p       +16.0%p
```

**Sonnet은 확실한 것에서 Opus를 거의 따라잡으면서(1.8%p 차) 의심스러운 것은 덜 집는다.**
Opus는 확실한 것에서 Sonnet보다 1.8%p 나은 대신 의심스러운 것을 16%p 더 집는다.

### 2.3 실제 항목 — 무엇을 더 잡았나

**Opus만 잡은 1/3 단독 항목 (21개)** — 성격이 갈린다

진짜 막힌 지점:
- 팀장은 유료 파서도 LLM도 안 된다고 함
- 가비지 인 가비지 아웃 (후보 문서 품질 문제)
- 코드 읽기 능력만으로 동시성·메모리 누수·네트워크 지연은 잡히지 않아 dry run 보완 필요

잡음:
- CSS는 인간 전문가가 너무 드물다 *(일반론)*
- CS 기초가 없거나 약하다 *(자기 상태 서술)*
- 짧은 파이썬 적응 시간 *(사실 서술)*

중복 — 병합 실패로 이중 계산:
- 느린 코랩
- 코랩이 느려서 한 페이지에 작성해야 했음

**Haiku만 놓친 3/3 확실 항목 (6개)** — 전부 진짜다

- 오류의 판단 주체 X 오류의 뭘로?
- 공식문서 내용을 프로젝트에 적용시키는데 어려움이 있었다
- 회사 업무 기한 대처법을 모르겠다
- 줌이 잘 안될 때
- 비콘 인식 문제

**셋 다 놓친 3/3 항목 (3개)** — 공통 약점

- 검증력: 답을 의심하고 다루는 능력 ?
- 라이브 코딩과 라이브 스피킹에서 자신감이 드러나지 않는다
- 스스로 검증하고 판단하는 능력이 떨어짐

셋 다 **자기 능력에 대한 반성**이다. 프롬프트가 "막힌 것"의 예시로 기술적 문제
(`???`, 헛점)만 들었기 때문으로 보인다.

## 3. 판정

| 모델 | 확실한 것 | 애매한 것 | 판정 |
|---|---|---|---|
| Haiku 4.5 | 70.2% | 50.9% | 놓침이 실질적 문제 — 3/3 항목 6개를 혼자 놓침 |
| **Sonnet 5** | **80.7%** | **54.3%** | **균형이 가장 좋음** — 확실한 건 Opus의 98% 수준, 잡음은 Haiku 수준 |
| Opus 5 | 82.5% | 70.3% | 과잉 경향 — 우위의 상당 부분이 잡음·중복에서 옴 |

**Sonnet 5를 채택한다.**

Opus가 절대 점수는 높지만, 확실한 항목에서의 이득(+1.8%p)에 비해 애매한 항목을
과도하게(+16.0%p) 집어 온다. 입력·출력 가격이 Sonnet의 1.7배이고 분량이 44% 길다는
점까지 더하면 값을 하지 않는다.

Haiku는 3/3 확실 항목 6개를 혼자 놓쳤다. 일지의 목적이 "내일 뭘 해야 하나"에
답하는 것이고 그 답이 막힌 지점에서 나온다면, 이 누락은 기능의 핵심을 훼손한다.

## 4. 길이 제한 폐지

프롬프트에 "대개 500자 안쪽이면 충분하다"고 명시했으나 세 모델 모두 초과했다
(567 / 618 / 890자). 이유는 두 가지다.

**첫째, LLM은 길이 제약을 신뢰성 있게 따르지 못한다.** 토크나이저가 단어가 아니라
토큰 단위로 동작해 모델이 글자 수를 정확히 인지하지 못하고, 학습 데이터에 엄격한
길이 제약 예시가 드물다. GPT-4급 모델도 "500단어 이내" 요청을 자주 초과한다는
연구가 있다 (LIFEBench, arXiv:2505.16234; Following Length Constraints, arXiv:2406.17744).

**둘째, 길이를 점수화하면 비대칭이 생긴다.** 기존 평가에는 `concise` 지표가 있었다.

```
Opus가 더 잡아냈다  →  분모에 없는 항목이면 점수 반영 안 됨
Opus가 더 길어졌다  →  길이는 정확히 측정되어 감점
```

**측정 가능한 것만 벌하고 측정 못 하는 것은 보상하지 않는** 구조였다. 이 때문에
처음 비교에서 "Opus가 기준을 덜 지켰다"는 잘못된 결론이 나왔다.

따라서:
- 프롬프트에서 "500자 안쪽" 문구 삭제
- `concise` 평가 지표 삭제 (길이는 참고값으로만 표시)

분량은 자료의 양에 맞춘다는 원칙만 남긴다.

## 5. 측정에 남은 한계

**중복이 이중 계산된다.** 병합 임계값 0.60이 긴 문장에서 실패한다.
`느린 코랩`과 `코랩이 느려서 한 페이지에 작성해야 했음`이 갈라져 두 항목으로 남았고,
둘 다 잡은 Opus가 점수를 두 번 받았다. 임계값을 더 낮추면 오합침이 생기므로,
항목을 짧은 구절로 정규화한 뒤 비교하는 편이 맞다.

**길이 효과를 분리하지 못했다.** Opus가 44% 길어 우연히 더 걸렸을 수 있다.
3/3 구간에서도 앞서므로 순전히 길이 때문은 아니지만, 기여도를 정량화하지 못했다.
길이를 맞춘 비교(같은 분량 제한 아래 재생성)가 필요하다.

**단독 항목 175개(58%)에 오탐이 섞여 있다.** `min_support=2`로 거르면 오탐이 줄지만
진짜인데 한 모델만 본 항목도 함께 사라진다. 참값은 두 기준 사이에 있다.
풀 파일은 사람이 편집할 수 있으므로, 분모가 큰 날부터 검토해 정리하면 개선된다.

**세 모델이 모두 Claude다.** 계열이 같으면 공통으로 놓치는 것이 있을 수 있다.
실제로 3/3 항목 3개를 셋 다 놓쳤고, 그 셋이 모두 같은 유형(자기 능력에 대한 반성)이었다.

## 6. 재현 방법

```bash
# 1. 분모 풀 생성 (1회, 55일 × 3모델)
uv run python -m scripts.build_blocker_pool alex

# 2. 검토 — 분모가 큰 날부터
uv run python -m scripts.build_blocker_pool review alex

# 3. 채점 (API 호출 0회)
uv run python -m scripts.langsmith_eval local alex

# 4. LangSmith 실험
uv run python -m scripts.langsmith_eval upload alex
uv run python -m scripts.langsmith_eval run alex --model claude-sonnet-5
```

관련 파일

| 경로 | 내용 |
|---|---|
| `logs/alex/<date>.md` | 생성된 일지 |
| `logs/alex/<date>.sources.json` | 그날의 원자료 (채점 근거) |
| `logs/alex/<date>.blockers.json` | 막힌 것 분모 풀 (사람이 편집 가능) |
| `logs/alex-v1/` | 기준 도입 전 일지 (비교용 보존) |
| `logs/alex-reference/` | 사람이 쓴 기준 일지 5일 (참고용) |
