01

배경

깊은 배경 — 이 시스템은 무엇을 하는가

건너뛰어도 좋다

벡터 검색과 RAG에 익숙하다면 좁은 배경으로 바로 넘어가도 된다.

나의 사관일지는 사용자가 남긴 흔적 — 학습 문서, git 커밋, AI 대화 — 을 날짜와 함께 모아 두었다가 세 가지 질문에 답하는 프로그램이다. 내일 뭘 해야 하나, 지금까지 뭘 했나, 전에 그게 뭐였나. 조선시대 사관이 매일의 일을 기록했듯이.

자료는 임베딩되어 벡터 데이터베이스에 저장된다. 임베딩은 글을 숫자 벡터로 바꾸는 일이고, 뜻이 비슷한 글은 벡터 공간에서 가까이 놓인다. 그래서 "비슷한 내용 찾기"가 "가까운 점 찾기"가 된다. 각 벡터에는 메타데이터가 붙는데, 이 프로젝트에서 가장 중요한 것이 date다. 날짜로 걸러야 그날의 일지를 쓸 수 있기 때문이다.

좁은 배경 — 일지 층이 서 있는 자리

원문을 그대로 두고 검색만 하면 문제가 생긴다. 사용자가 "지난주에 뭐 했지?"라고 물으면 관련 조각 몇 개가 나올 뿐, 그 주에 무슨 일이 있었는지는 알 수 없다. 그래서 원문 위에 일지라는 요약 층을 둔다.

이번 작업 직전의 상태는 이랬다. 일지를 생성하는 코드가 있고, 프롬프트에 ## 배운 것 — 핵심 개념을 항목별로 라고 적혀 있었다. 그리고 일지가 잘 쓰였는지 재는 평가 코드가 있었다.

문제

"핵심"이 무엇인지는 어디에도 정의되어 있지 않았다. 그런데도 평가는 이미 존재했다. 무엇이 정답인지 정하지 않은 채 채점표부터 만든 셈이다.

02

직관

요약을 "많이 담았는가"로 재면 안 된다

처음 만든 평가는 이렇게 동작했다. 사람이 쓴 기준 일지를 정답으로 두고, 모델이 쓴 일지와 용어가 얼마나 겹치는지를 커버리지로 계산한다. 많이 겹칠수록 좋은 점수.

작은 예로 보면 문제가 바로 드러난다. 어떤 날의 원자료에 이런 것들이 있다고 하자.

원자료 항목성격요약에 필요한가
어텐션 수식을 손으로 계산함직접 한 일필요
"??? 헛점, 전개가 매끄럽지 않다"막힌 지점필요
비디오 메모리 16GB → 32GB, 48GB, 64GB맥락 없는 숫자불필요
ngrok 링크참조불필요

좋은 요약은 아래 둘을 버려야 한다. 그런데 용어 겹침으로 재면 버릴수록 점수가 떨어진다. 지표가 요약과 정반대 방향을 가리킨다.

핵심

요약의 품질은 담은 양이 아니라 고른 안목이다. 무엇을 버렸는지를 벌하는 지표는 요약을 요약이 아니게 만든다.

실제로 이 지표는 두 방향으로 동시에 왜곡되어 있었다. 한 날짜를 뜯어 보면 이렇다.

지표표시값왜곡이유
커버리지22.3%실제보다 낮음 기준 일지 용어 188개 중 48개가 내 문체였다. "살펴봤다", "이어졌다" 같은 말이 분모에 들어가 있었다
근거성76.8%실제보다 높음 "지어낸 용어" 23개 중 20개가 "개념", "기반", "주요" 같은 일반 명사였다. 진짜 환각은 3개뿐

기준은 목적에서 나온다

기준을 임의로 정할 수는 없다. 이 시스템이 답해야 할 세 질문에서 끌어내면 담을 것이 그대로 도출된다.

담는 것어느 질문에 답하나판별법
한 일지금까지 뭘 했나직접 만들고·계산하고·커밋한 것. 읽기만 한 것과 구분
막힌 것내일 뭘 해야 하나???, "헛점", "매끄럽지 않다", 의문형 메모
정한 것지금까지 뭘 했나결정·구상·방향
예정내일 뭘 해야 하나일정, 마감, "다음 시간 예고"
다룬 주제전에 그게 뭐였나개념 이름만. 설명은 하지 않음
대전제

일지는 원문을 대체하지 않는다. 미적분학의 기본 정리를 일지에 옮겨 적을 이유가 없다. 원문이 벡터DB에 그대로 있기 때문이다. 개념 설명을 빼면 일지는 짧아지고, 그 자리에 한 일·막힌 것·예정이 들어간다.

사람의 눈은 채점자로 부적합하다

작업 도중 같은 실수를 두 번 했다. 모델이 쓴 일지를 읽고 "이건 원자료에 없는 내용이다, 환각이다"라고 판정했는데, 두 번 다 틀렸다.

내가 읽은 양실제 원자료결과
2026-06-15700자4,105자 환각이라 지목한 neo4j, jena, hnsw, chroma, 원핫, crud — 전부 원자료에 있었다
2026-07-27600자4,475자 환각이라 지목한 Next.js, LangGraph, FBL, prefill/decode — 전부 원자료에 있었다

원인은 단순하다. 원자료를 화면에 띄울 때 앞부분만 잘라서 봤다. 4,000자짜리 자료에서 600자만 읽고 "없다"고 단정한 것이다. 사람은 긴 자료를 끝까지 읽지 않는다.

그래서

자동 평가가 필요한 이유는 "빠르니까"가 아니라 "사람보다 정확하니까"다. 코드는 4,475자를 전부 확인한다. 지치지도, 앞부분만 보고 넘어가지도 않는다.

일지는 검색이 실패하는 자료로 가는 다리

일지에 개념 이름을 남길지 말지를 정하려면, 원문 검색이 실제로 잘 되는지부터 확인해야 했다. 실측하니 절반만 동작했다.

검색어1위 결과판정
야코비 행렬2026-06-13 원문 — 정확히 일치성공
동치관계 조건2026-05-23 AI 대화 — 한국어 문장성공
코시 수열2026-06-05 CNN 역전파 수식실패

코시 수열은 실제로 2026-06-13 원문에 있는데 검색이 찾지 못했다. 그 청크가 이렇게 생겼기 때문이다. 

```math
\begin{gather*}
\lim _{ n \to \infty } a _{ n } = \sqrt{ 2 }
\end{gather*}
```

LaTeX 덩어리는 임베딩 품질이 나쁘다. 한국어 문장이 거의 없으니 "코시 수열"이라는 질의와 벡터 거리가 멀다. 대신 다른 날의 수식 덩어리끼리 서로 가까워서 엉뚱한 것이 1위가 된다.

일지는 깨끗한 한국어로 쓰인다. 그래서 일지가 이 구멍을 메운다.

다만 일지가 검색에 걸려야 이 다리가 작동한다. 그래서 개념 이름을 어떻게 적을지도 실측했다. 같은 날짜의 일지를 두 형태로 만들어 유사도를 쟀다.

질의이름만 나열이름 + 한 줄
코시 수열0.38880.5231+34%
코시 수열이 뭐였지0.35270.4814+36%
야코비 행렬0.24450.2327−5%

이름만 18개를 나열하면 벡터가 그 18개의 평균 위치로 가는데, 평균은 어느 개념과도 멀다. 한 줄 설명이 붙으면 벡터가 그 개념 쪽으로 당겨진다.

그런데도 이름만 쓰기로 했다

마지막 행이 이유다. 목록이 길어질수록 각 항목의 신호가 희석되므로, 한 줄을 붙여도 한계가 있다. 개념 검색을 일지가 책임지게 만들려면 개념별로 노트를 따로 두는 층이 필요한데, 후보 용어를 세어 보니 55일치에서 6,479개가 나왔다. 빈도 1위는 피드백(52일)으로 개념조차 아니었다. 자동 추출이 불가능하다는 뜻이므로, 그 층은 뒤로 미뤘다.

03

코드

파일 순서가 아니라 데이터가 흐르는 순서로 본다. 재료를 만들고 → 기준을 넣고 → 채점한다.

1. 재료를 만든다

실제 데이터에는 문서만 있는 날이 대부분이었다. 일지 생성을 시험하려면 하루에 문서·커밋·대화가 함께 있어야 하므로, 각 날짜의 실제 TIL 내용을 근거로 그날 있었을 법한 커밋과 대화를 생성했다.

반드시 표시한다

이 시스템은 "실제로 무엇을 했는가"의 기록이다. 지어낸 커밋이 진짜와 구분되지 않으면 나중에 "6월 13일에 뭐 했지?"에 소설이 나온다. 그래서 모든 더미에 synthetic=True를 박았다. 나중에 골라내거나 일괄 삭제할 수 있다. 

# scripts/seed_dummy_sources.py
metadata={
    # 실제 커밋 SHA가 아니므로 합성임이 드러나는 형태로 만든다
    "commit_sha": f"synthetic-{day['date']}-{index}",
    "date": day["date"],
    "date_origin": "synthetic",
    "synthetic": True,
}

결과는 55일 전부가 세 종류를 갖추게 되었다.

2. 기준을 프롬프트에 넣는다

이전 프롬프트에서 담을 것을 정하는 문장은 사실상 한 줄뿐이었다.

## 배운 것 — 핵심 개념을 항목별로. 자료에 나온 용어를 사용
# "핵심"이 무엇인지 정의되어 있지 않다

새 프롬프트는 담을 것과 버릴 것을 모두 명시한다.

# scripts/generate_journals.py — SYSTEM
일지는 원문을 대체하지 않는다. 개념 설명은 원문에 그대로 남아 있으므로
옮겨 적지 않는다.

## 담는 것
1. 한 일 — 직접 만들고, 계산하고, 커밋한 것. 읽기만 한 것과 구분한다.
2. 막힌 것 — `???`, "헛점", "매끄럽지 않다" 같은 표시, 의문형 메모.
3. 정한 것 — 결정, 구상, 방향.
4. 예정 — 일정, 마감, "다음 시간 예고" 같은 메모.
5. 다룬 주제 — 개념 이름만 나열한다. 설명하지 않는다.

## 버리는 것
- 자료에 없는 내용. 이건 선택이 아니라 금지다.
- 개념의 상세 설명. 이름만 남기고 내용은 원문에 맡긴다.
- 문장이 끊겨 복원할 수 없는 조각.
- 맥락 없는 숫자 나열, 참조 링크.

개념 설명을 뺐으므로 자료가 많아도 대개 500자 안쪽이면 충분하다.

3. 원자료를 채점 기준으로 삼는다

가장 중요한 변화다. 이전에는 사람이 쓴 기준 일지와 비교했고, 그래서 문체 차이가 점수로 둔갑했다. 새 평가는 원자료와 비교한다. 

- def score(candidate, reference, source):
-     ref = terms(reference)              # 사람이 쓴 일지의 용어
-     covered = cand & ref
-     coverage = len(covered) / len(ref)  # ← 문체가 분모에 섞인다

+ def score(candidate, source, chunks):
+     """
+     기준 일지와 비교하지 않는 이유: 일지는 요약이므로 정답이 하나가 아니다.
+     사람이 쓴 문장과 용어가 겹치는지를 재면 문체 차이가 점수로 둔갑한다.
+     대신 기준 문서가 "반드시 담으라"고 정한 것만 원자료에서 찾아 확인한다.
+     """

지표는 넷이고, 각각 기준 문서의 항목에 대응한다.

# ① 커밋 반영 — 그날 커밋한 내용이 일지에 나타나는가
commits = find_commits(chunks)          # git_log는 구조화돼 있어 자동 추출 가능

cand_en = {t for t in terms(candidate) if t[0].isascii()}

4. LangSmith에 붙인다

용어를 옮기면 이렇게 대응된다. 두 파일 묶음을 업로드해 맞대는 것이 아니라, 기준을 Dataset으로 올리고 모델마다 Experiment를 돌린다.

04

결과

이 절은 한 번 뒤집혔다

처음 측정에서는 「막힌 것 포착」이 90% → 96%로 개선된 것으로 나왔다. 그러나 그 수치는 정규식 분모로 잰 값이었고, 55일 중 43일(78%)에서 분모가 0이라 자동 만점이 나오고 있었다. 분모를 바로잡자 결론이 반대로 뒤집혔다. 아래는 고친 분모(300개)로 다시 잰 값이다.

지표가 못 본 것

Opus가 가장 높지만, 우위가 어디서 오는지를 나누면 판단이 달라진다. 3/3 합의 항목은 진짜일 가능성이 높고, 1/3 단독 항목은 오탐일 가능성이 높다.

Sonnet을 넣고 보면 위치가 분명해진다. 확실한 구간에서 Haiku 70.2% → Sonnet 80.7% → Opus 82.5%로 Sonnet이 Opus를 거의 따라잡는다(1.8%p 차). 의심 구간에서는 50.9% → 54.3% → 70.3%로 Opus만 크게 뛴다(16.0%p). Sonnet은 확실한 것을 거의 다 잡으면서 의심스러운 것은 덜 집는다.

채택

Sonnet 5. 길이 제한을 없앤 최종본은 커밋 반영 100%, 막힌 것 70.3%, 환각 없음 96.5%, 평균 681자다. 제한을 없앴는데 618자 → 681자로 63자만 늘었다 — 애초에 그 제한이 작동하지 않았다는 증거다.

남은 오차
