# 8월 3일 — 측정 도구를 만들다 생긴 함정

일지 품질을 재려고 평가 시스템을 만든 날이다. **문제는 재는 대상이 아니라 자[尺]에서 나왔다.**

오전에는 웹 UI와 임베딩 비동기화를 고쳤고, 오후 전체가 평가 체계에 들어갔다.

## 오전 — 조용히 실패하던 웹 UI

### 문제: 422가 성공처럼 보였다

`log_maker.html`이 `{req, thread_id}`를 보내는데 백엔드 `QueryReq`는 `{message, user_id}`를 기대해 HTTP 422가 났다. 그런데 `log_maker.html:375-380`이 **`response.ok`를 확인하지 않아** 422가 성공으로 표시됐다.

파이썬에서 직접 부르면 임베딩·날짜 검색·일지 저장이 전부 정상이었고 브라우저 경로만 막혀 있었다. 그래서 오래 발견되지 않았다.

**결정**: 필드만 맞추지 않고 `log_maker` 자체를 폐기했다. `/user/{user_id}` 채팅이 이미 정상 동작하고 있어 화면을 두 벌 유지할 이유가 없었다.

### 함께 드러난 것

| 증상 | 진짜 원인 |
|---|---|
| `/settings` 500 | 절대 임포트 (`storage.models`, `tools.embedding`) |
| `/debugger` 500 | `templates/debugger.html` 파일이 아예 없었음 |
| 소스를 지워도 검색에 계속 나옴 | HTTP 삭제 경로가 벡터DB를 정리하지 않음 |

마지막 항목은 **설정 화면 삭제와 Agent 도구의 동작이 다르다**는 것이 단서였다. 도구 쪽은 `_delete_source_embeddings`를 부르는데 라우터 쪽은 SQLite 레코드만 지우고 있었다. 같은 일을 하는 코드가 두 벌 있으면 한쪽만 고쳐진다.

### 임베딩 비동기화

임베딩이 요청을 붙잡고 있어 채팅이 멈췄다. 백그라운드 스레드로 옮기고(0.06초 즉시 반환), 진행률을 DB 컬럼에 적고, 화면이 폴링하도록 했다(임베딩 중 2초 / 유휴 15초).

여기서 **stale 판정**이 함께 필요했다. 서버가 임베딩 도중 죽으면 상태가 영원히 `IN_PROGRESS`로 남아 재시도가 막히기 때문이다. 30분을 넘기면 중단된 작업으로 본다.

## 오후 — 평가 지표가 만들어낸 거짓 결론들

여기가 이날의 핵심이다. 자세한 것은 `docs/일지평가-함정기록.md`(함정 9개)에 있고, 아래는 **원인이 같은 것끼리 묶은 것**이다.

### ① 기준을 정하지 않고 지표부터 만들었다

"좋은 일지"의 정의 없이 커버리지·근거성부터 계산했다. `generate_journals.py`의 SYSTEM 프롬프트가 "핵심 개념"을 정의하지 않은 채였다.

나중에 기준을 정하고 프롬프트에 박았다 — **담을 것**(한 일 / 막힌 것 / 정한 것 / 예정 / 다룬 주제), **버릴 것**(자료 밖 설명, 개념 상세 설명, 맥락 없는 숫자, 참조 링크, 복원 불가 조각).

| 지표 | v1 (옛 기준) | v2 (새 기준) |
|---|---|---|
| 커밋 반영 | 98% | **100%** |
| 막힌 것 포착 | 90% | **96%** |
| 환각 없음 | 93% | **96%** |
| 평균 길이 | 803자 | 574자 (29%↓) |

**모델을 바꾸지 않고 프롬프트만 고쳐 얻은 결과다.** 나중에 모델 업그레이드는 비용 5배에 1~4%p였다. 프롬프트 엔지니어링이 모델 선택보다 효과적이었다.

### ② 지표의 분모에 내 문체가 섞여 있었다

커버리지 22.3%가 나와 "많이 놓쳤다"고 판단했다. 누락 146개를 뜯어보니:

- **98개** — 원자료에 있는데 빠뜨린 것 (진짜 누락)
- **48개** — 원자료에 없고 내 일지에만 있는 표현 (**내 문체**)

분모가 문체로 부풀려져 있었다. 근거성 76.8%도 일반명사가 섞여 실제로는 ~97%였다.

**두 지표가 반대 방향으로 왜곡돼 있었다.** 커버리지는 낮게, 근거성은 높게.

부수적 원인도 있었다. `_hit()`이 단순 부분문자열 매칭이라 원자료의 `overfitting`이 일지에서 "오버피팅"으로 쓰이면 0점이었고, STOPWORDS가 부족해 `파일`·`추가`·`이랑` 같은 말이 분모를 부풀렸다.

### ③ 원자료를 잘라 읽고 "환각"이라 판정했다 — 두 번

4,000자 중 600자만 읽고 neo4j·chroma를 환각으로 몰았다. **전부 원자료에 있었다.** 실제 환각은 `300차원`, `tensor` 정도뿐이었다.

사람의 눈으로 환각을 판정하는 것이 안 된다는 것이 여기서 확인됐고, 자동 평가가 필요하다는 근거가 됐다.

### ④ 분모가 0이라 자동 만점이 나오고 있었다

```python
score = hits / len(blockers) if blockers else 1.0   # ← 분모 0이면 100점
```

정규식으로 뽑은 분모가 **55일 중 43일(78%)에서 0개**였다. 94~98%라는 높은 점수의 대부분이 채점 결과가 아니라 자동 만점이었다.

### ⑤ LLM에게 매번 물으면 재현되지 않는다

분모를 LLM으로 뽑게 했더니 같은 자료인데 3번 돌려 **6개, 10개, 8개**가 나왔다. 항목 자체도 실행마다 달라졌다. 일지를 고치지 않아도 점수가 30%p씩 움직인다.

Sonnet 5·Opus 5는 `temperature`가 제거돼 결정론을 요청할 방법도 없다.

| 방식 | 재현성 | 정확도 |
|---|---|---|
| 정규식 | 완벽 | 낮음 (분모 0으로 고정) |
| LLM 매회 호출 | **없음** (6~10개) | 높음 |
| **TREC 풀링** | 완벽 | 높음 |

**채택한 해법 — 분모를 한 번만 만들어 파일로 고정한다.**

`scripts/build_blocker_pool.py`가 Haiku·Sonnet·Opus 3개 모델로 각각 추출하고, 로컬 임베딩 코사인 유사도로 병합해 `<date>.blockers.json`에 저장한다. 이후 채점은 이 파일과 대조만 한다.

- LLM 호출 165회(55일×3모델) → **0회**
- 점수 변동 제거
- **사람이 파일을 열어 오탐을 지울 수 있다**
- 병합 임계값 0.60은 실측으로 정했다 — 합쳐야 할 쌍은 0.64~0.80, 아닌 쌍은 0.12~0.28에 분포해 그 사이가 넓게 비어 있다

여러 모델의 합집합을 쓰는 이유는 정보검색 평가(TREC)와 같다. **한 모델이 만든 목록으로 채점하면 그 모델의 관점이 곧 정답이 되어 자기 자신에게 유리해진다.**

### ⑥ 그래서 "모델 차이 없음"이라는 결론이 뒤집혔다

이것이 이날 가장 중요한 사건이다.

| 시점 | 결론 |
|---|---|
| 분모 고치기 전 | "세 모델 차이 최대 3.7%p, 무의미하다" |
| 분모 고정 후 | Haiku 60.3% / Sonnet 68.0% / **Opus 75.7%** — **15.4%p** |

**불완전한 분모가 "차이 없음"이라는 거짓 결론을 만들어냈다.**

그리고 합의 수준별로 나눠 보니 판정 근거가 분명해졌다:

| support | 항목수 | Haiku | Sonnet | Opus |
|---|---|---|---|---|
| **3/3** (확실) | 57 | 70.2% | **80.7%** | 82.5% |
| 2/3 | 68 | 66.2% | 72.1% | 80.9% |
| **1/3** (오탐 의심) | 175 | 50.9% | **54.3%** | 70.3% |

**Opus의 우위가 오탐 의심 구간에서 가장 크다(+19.4%p).**

→ **Sonnet 5 채택.** 확실한 항목에서 Opus의 98% 수준(80.7 vs 82.5)을 내면서, 의심스러운 항목은 16%p 덜 집는다. `src/llm_router.py`의 `ANTHROPIC_MODEL`이 이것이다.

### ⑦ 길이를 점수화해 비대칭이 생겼다

`concise = min(1.0, 500 / length)` — **지표 자체가 짧은 답을 선호하도록 설계돼 있었다.**

Opus가 500자 지시에 890자를 쓴 것은 게을러서가 아니라 **더 많이 찾아냈기 때문**이었다(같은 자료에서 「한 일」 4개, 「막힌 것」 6개 vs Haiku 각 2개). 그런데 추가로 잡은 항목은 분모에 없어 점수에 반영되지 않고, 길이만 정확히 측정돼 감점됐다.

**측정 가능한 것만 벌하는 구조였다.** 웹 검색으로 확인하니 알려진 문제였다 — 길이 제약 미준수(LIFEBench), 불완전한 정답셋(TREC pooling bias), verbosity bias(LLM-as-Judge).

→ `concise` 삭제, `length`는 참고값(`score: None`)으로만, 프롬프트의 500자 제한도 폐지.

### ⑧ 개념 노트 층을 성급히 설계했다

"학습한 개념을 키워드로 저장하고 그 키워드로 원문을 조회하자"는 구조를 설계했다. 그런데 실제로 세어 보니 55일에서 고유 용어가 **6,479개**였고, 빈도 상위는 `피드백`(52일)·`https`(51일)처럼 개념이 아니라 노이즈였다.

**빈도나 용어 추출로는 개념과 노이즈를 구분할 수 없다.** 개념 자동 추출은 불가능하다고 결론짓고, 개념 노트 층은 일지가 쌓인 다음으로 미뤘다.

측정으로 얻은 부수적 사실: 이름만 나열하는 것보다 **이름+한 줄 설명**이 검색 신호가 34~36% 높다(0.3888→0.5231). 다만 항목이 많아지면 신호가 희석된다.

# 8월 4일 — 조용히 실패하던 수집 파이프라인

이날의 공통 주제는 하나다. **실패가 성공처럼 보였다.**

## 식별된 공백 (C1~C6)

| # | 문제 | 왜 안 보였나 |
|---|---|---|
| C1 | chatlog·memsearch 수집기가 빈 껍데기 | 등록·임베딩이 **성공**으로 끝남 (0건 수집) |
| C2 | git_log 소스가 갱신되지 않음 | clone 이후 커밋이 영영 안 들어옴 |
| C3 | 원본 파일 삭제 시 청크 잔류 | 지운 문서가 계속 검색됨 |
| C4 | 텅 빈 커밋 문서 저장 | merge 커밋은 `--numstat`이 아무것도 안 내보냄 |
| C5 | 제외 건수를 세지 않음 | 유실이 통계에 안 잡힘 |
| C6 | 21개 초과 파일 절단 | 잘린 사실이 안 알려짐 |

### C2 — 가장 전형적인 silent failure

```python
if not repo_dir.exists():
    clone(...)
# else 가 없다
```

이미 받아둔 저장소는 **갱신되지 않았다.** 에러도 경고도 없이, clone 시점 이후의 커밋이 영원히 수집되지 않는다.

→ `_sync_repo` 공통 함수로 통합(+70/−33). 처음엔 `--mirror`를 택했다(bare는 fetch refspec을 설정하지 않아 조용히 아무것도 안 하지만, mirror는 `+refs/*:refs/*`를 설정한다). 2.2MB → 752KB.

`tests/unit/test_sync_repo.py`에 회귀 테스트를 붙이고, **수정 전 코드로 되돌리면 5개가 FAIL하는 것을 확인**해 테스트의 실효성을 입증했다.

### L3 — 검색이 조용히 잘리고 있었다

가장 실질적인 피해였다. 2026-07-28에 **44건이 저장돼 있는데 `limit=5`로 39건(89%)이 에러도 경고도 없이 잘려나갔다.**

원인이 셋 겹쳐 있었다:
1. LLM이 `reference_len`을 임의로 5로 설정
2. 날짜 필터는 정확일치라 문서 사이에 우열이 없음 → 순위가 무의미
3. 결과적으로 "중요한 5건"이 아니라 **"먼저 저장된 5건"**이 남음

나중에 임베딩한 소스가 통째로 밀려난다.

→ `reference_len` 제거, `MAX_RESULT_CHARS=40,000` 글자 예산 도입, 축약 단계, **제외 건수와 담긴 기간 명시.**

## 커밋 날짜 묶기 (C4·C5와 함께)

커밋 1건 = 문서 1개 구조에서 67건 14,221자 중 **53%가 파일 변경 목록, 29%가 날짜+작성자 반복**이었다.

→ 하루당 문서 1개로 묶어 **67개 → 8개(69% 감소)**. merge 2건·빈 커밋 1건을 제외하고 `skip_reasons`에 기록(C5가 손실을 안 세고 C4가 빈 문서를 저장해서 유실이 통계에 안 잡히던 구조를 함께 해소).

**발견한 부작용**: 하루 요약이 `CHUNK_SIZE=2000`에 걸려 4청크로 쪼개졌다. 제목 줄과 본문이 갈라져 고아 청크가 된다. → `DAILY_SUMMARY_TYPES`로 분할에서 제외(날짜 필터로 조회하므로 길어도 불리하지 않다).

**검증**: L1 대조로 원본 67개 중 merge 2 + 빈 커밋 1을 뺀 64개 sha가 저장분과 완전 일치.

## 진단을 스스로 뒤집은 건 — `user_id` 누락

**최초 진단**: "모델이 `user_id`를 자꾸 빠뜨린다." → `Annotated[str, InjectedState("user_id")]`로 스키마에서 숨기는 방안까지 설계했다.

**정정**: LangSmith로 실측했다(2026-07-22~08-04, 도구 호출 177건).

| 경로 | 호출 | `user_id` 누락 |
|---|---|---|
| 스크립트 직접 호출 | — | **14건 (전부)** |
| 에이전트 경유 | 23건 | **0건** |

**모델은 한 번도 빠뜨리지 않았다.** 진짜 원인은 `test_log_tools.py`가 커밋 `9c3f4e1`의 시그니처 변경을 따라가지 못한 낡은 호출이었다.

## git log 명령 자체의 단순화

**1차**: `--numstat` → `--name-only`. 전체 4,393자 중 숫자가 10%를 차지했고, "+6368줄" 같은 큰 값이 실은 문서 파일 추가였다. `lines_added`/`lines_deleted` 메타데이터 제거.

**2차**: `--graph --all` 제안이 나왔으나 **실측으로 반박**했다. `--graph`는 그래프 문자(`*`, `|\`, `|/`)를 줄 앞에 붙여 파서의 마커 탐지가 실패한다(71줄 파싱 실패, 마커가 맨 앞인 줄 0개).

**3차(최종)**: `--mirror` → `--filter=blob:none --no-checkout`. 커밋 메타데이터만 읽으므로 파일 본문(blob)을 아예 받지 않는다. **756K → 168K (78% 감소).**

## C1 — 대화 로그 수집

일지의 「막힌 것 / 예정」 항목이 늘 비어 있었다. 커밋과 문서에는 그 정보가 없기 때문이다.

Claude Code 트랜스크립트를 조사하니 12세션 19MB 중 **사람이 실제로 친 말은 179건 17KB(1%)**뿐이었다. 나머지는 도구 호출·결과·thinking이다. 약 567:1 압축.

→ `src/tools/chatlog.py` 신규. `MIN_TURN_CHARS=12`(선택지 응답 제외), `MAX_TURN_CHARS=600`(붙여넣기 상한). 노이즈(도구가 끼워 넣은 텍스트)가 하루치의 67%를 차지해 접두사로 걸러낸다. `tests/unit/test_chatlog.py` 회귀 테스트 포함.

## 토큰 비용 — 조회 결과가 대화에 눌러앉았다

ChromaDB는 날짜로 거르는데, **조회 결과 10,321토큰이 `InMemorySaver`에 남아 이후 모든 호출에 재전송**됐다.

| 방식 | 토큰 | 비용 |
|---|---|---|
| 같은 thread 5회 | 275,265 | $0.83 |
| 새 대화마다 | 63,285 | $0.19 |

시나리오 실측에서 나온 **비직관적 결론**: 스레드 분리와 프롬프트 캐싱은 보완재가 아니라 **대체재**다. 분리하고 나면 매번 새 도구 결과라 캐시 효율이 12%로 떨어진다.

"압축하면 데이터가 유실되지 않느냐"는 우려에 대해서는 — 컨텍스트 61,882토큰은 1M 창의 6%라 압축이 불필요하고, **유실은 이미 벌어지고 있으므로 예산 상향은 유실을 고치는 것이지 만드는 게 아니다**로 정리했다.

→ 커밋 `a1d8fab perf: stop resending tool results and cache the prompt prefix`가 여기에 해당한다(`prune_tool_traffic` 노드 + `cache_control`).

> 아래 상태는 2026-08-05에 코드를 직접 확인한 것이다.

## 🔴 `SHRINK_STEPS` — 지금도 데이터가 유실되며, 8/4 이후 더 나빠졌다

`src/tools/log.py:43`의 `SHRINK_STEPS = (3, 0)`이 그대로 살아 있다.

문제는 **커밋 날짜 묶기가 문서 구조를 바꿨다는 것**이다. 문서 본문은 이제 이렇다:

```
[2026-08-04] yuta_logagent — 커밋 4건

한 일:
- fix: keep git_log sources up to date     ← 이제 이게 커밋 메시지다
- feat: collect agent chat logs
```

`_shrink_commit`은 `- `로 시작하는 줄을 지운다. **예전엔 그게 파일 경로였는데, 지금은 커밋 메시지 본문이다.**

| 단계 | 결과 |
|---|---|
| `keep=3` | 커밋 메시지가 3개로 잘림 |
| `keep=0` | `if keep_files:`가 False라 "외 N개"도 안 붙고 **내용이 통째로 사라짐** |

`keep=0`이면 남는 것은 제목 줄과 `한 일:` 뿐인 빈 껍데기다.

**부수 문제 2가지**:
- 사용자에게 나가는 안내문이 `"커밋의 파일 변경 목록을 생략했습니다"`인데, 실제로 지운 것은 내용 전부다 — **사실과 다르다**
- `agent_chatlog`도 같은 `- 발화` 구조인데 축약 대상이 아니다(`source_type == "git_log"` 조건). 축약되지 않고 **문서째로 버려진다**

**기록된 실측 피해**: 기간 조회(7/09~8/03)에서 59개 문서 중 35개만 표시, **7/28 이후 최신 29개 문서(47,930자)가 통째로 누락**. 날짜 정렬 때문에 최신부터 버려진다.

**테스트가 못 잡은 이유**: 30일치로는 `keep=3`(14,571자)에서 이미 예산 안에 들어와 `keep=0`까지 가지 않는다. 90일치를 써야 재현된다.

**제안된 수정** (`docs/gitlog-수집방식-변경계획.md`, 815줄, Task 6개, TDD 구성 — 미착수):
- `SHRINK_STEPS = (3, 0)` → `(20, 5)`, `keep=0` 제거
- `keep_files` → `keep_items`, `_shrink_commit` → `_shrink_daily` 개명
- `agent_chatlog`도 축약 대상에 포함

> **완화 요인**: 2026-08-05에 붙인 `generate_daily_journals`는 기간을 날짜별로 쪼개 처리하므로 **기간 일지 생성 경로에서는** 이 문제를 우회한다. 다만 `retriever_vectordb`를 직접 기간으로 부르는 경로는 그대로 노출돼 있다.

### `MAX_RESULT_CHARS`도 근거 없는 값이었다

40,000자는 "하루치는 대개 수천 자"라는 추측이었다고 기록에 인정돼 있다. 실측으로는 92일 조회에 183,519자(4.6배)가 필요하다.
