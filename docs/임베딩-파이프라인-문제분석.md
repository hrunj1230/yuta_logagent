### 검증 중 새로 발견한 문제

**P8. git이 한글 경로를 8진수로 이스케이프함** 🔴

`git log --name-only` 는 기본 설정에서 비ASCII 경로를 `"\355\232\214\352\263\240..."` 형태로 출력한다.
이 때문에 날짜 매핑이 실제 파일 경로와 매칭되지 않아, 한글 파일명 24개가 날짜를 얻지 못하고 수집에서 탈락했다.

`git -c core.quotepath=false log ...` 로 두 곳(`git_file_dates`, `_collect_git_log`)을 수정했다.
회귀 방지를 위해 한글 경로 테스트를 추가했다.

이 문제를 고친 뒤 수집 대상이 **35개 → 59개**로 늘었고, 날짜를 못 붙인 파일은 0개가 되었다.

### 증거

**510 / 572 = 89.2%** 가 Obsidian 플러그인 소스코드다.

### 원인

`src/tools/embedding.py:21`

```python
TEXT_EXTENSIONS = {".txt", ".md", ".py", ".js", ".tsx", ".jsx",
                   ".java", ".go", ".rs", ".c", ".cpp", ".h"}
```

- 확장자 화이트리스트에 `.js` 등 **코드 확장자가 포함**되어 있다.
- `_collect_git_files()`(L157)와 `_collect_local_files()`(L256)가 모두 `rglob("*")` 로 **전체 트리를 무조건 순회**한다.
- 제외 디렉토리 규칙이 없다 (`.obsidian`, `.git`, `node_modules`, `.venv`, `dist`, `build` 등).
- 파일 크기 상한이 없다. 실제로 `theme.css` 1.6MB, `main.js` 316KB 파일이 수집 대상 트리에 존재한다.

### 영향

- 검색 품질 붕괴. "저번에 뭐 했더라?" 질의 시 상위 결과 대부분이 플러그인 코드로 채워진다.
- 저장 공간 낭비 (P7 참조).
- 임베딩 시간 낭비.

### 확장 위험

현재는 TIL 저장소 하나만 등록된 상태다. 코드 저장소를 추가로 등록하면 **저장소 전체 소스코드가 그대로 임베딩**되어 오염도가 더 심해진다. 한 저장소에 문서와 코드 프로젝트가 섞여 있는 경우도 현재 구조로는 분리할 방법이 없다.

## 🔴 P2. 날짜 메타데이터가 생성되지 않음

### 증거

ChromaDB `embedding_metadata` 테이블에 존재하는 키 전체:

```
user_id, source_id, source_type, source_name,
file_path, file_hash, chunk_index, embedded_at
```

**`date` 키가 없다.**

`embedded_at` 의 실제 값을 확인한 결과, 전체가 동일한 값이다:

```
2026-07-29T00:47:34.713258
2026-07-29T00:47:34.713645
2026-07-29T00:47:34.713869
```

이는 **임베딩을 실행한 시각**이지 문서가 작성된 날짜가 아니다.

### 원인

`src/tools/embedding.py:170-180` (`_collect_git_files`), `:265-275` (`_collect_local_files`)

```python
metadata={
    ...
    "embedded_at": datetime.now().isoformat()   # 실행 시각
}
```

문서의 실제 날짜를 추출하는 코드가 전혀 없다. `Today I Learn/2026_05_14.md` 처럼 **파일명에 날짜가 명시되어 있는데도** 파싱하지 않는다.

`_collect_git_log()`(L228-241)만 `date` 키를 기록하지만, 값이 `2026-07-29 00:47:34 +0900` 형태의 ISO datetime이라 날짜 문자열과 직접 비교할 수 없다.

### 영향

프로젝트의 핵심 기능인 날짜 기반 조회("8월 1일에 뭐 했지?")가 원천적으로 불가능하다.

## 🔴 P3. 날짜 검색이 항상 실패하고 조용히 폴백함

### 원인

`src/tools/log.py:49-69`

```python
# 1차: 메타데이터 필터로 정확한 날짜 찾기
try:
    docs = reopened.get(where={"date": date_filter}, limit=k)   # ← date 키 없음
    if docs and docs.get('documents'):
        ...
    else:
        # 2차: 유사도 검색
        docs = reopened.similarity_search(f"작성 날짜: {date}", k=k)   # ← 무의미
except Exception as e:
    docs = reopened.similarity_search(f"작성 날짜: {date}", k=k)
```

1차 필터는 P2 때문에 **존재하지 않는 키**를 조회하므로 결과가 항상 비어 있다.
그 결과 2차로 `"작성 날짜: 2026-08-01"` 이라는 **문자열 자체를 임베딩해 의미 유사도 검색**을 수행한다.

날짜 문자열의 임베딩 벡터는 문서의 작성 날짜와 아무런 상관관계가 없다. 사실상 무작위 결과다.
게다가 P1으로 코퍼스의 89%가 플러그인 코드이므로, 반환되는 것은 대부분 자바스크립트다.

또한 실패가 `print("[DEBUG] ...")` 로만 기록되고 호출자에게 전달되지 않아, **검색이 실패했다는 사실 자체가 드러나지 않는다.**

### 원인 사슬

```
P1 (필터 없음)  ─┐
                  ├─→ 날짜 검색이 무관한 코드를 반환
P2 (날짜 없음) ─→ P3 (필터 실패 → 조용한 폴백) ─┘
```

P2만 고치고 P1을 두면 검색 정확도는 오르지만 여전히 플러그인 코드가 섞인다.
P1만 고치고 P2를 두면 코퍼스는 깨끗해지지만 날짜 조회는 여전히 불가능하다.
**세 문제는 함께 해결해야 한다.**

## 🟡 P4. 메타데이터 키 이름 불일치

`src/tools/log.py:77-79` 는 다음 키를 읽는다:

```python
source   = doc.metadata.get("source",  "unknown")
doc_type = doc.metadata.get("type",    "document")
```

```
날짜: 날짜 정보 없음
출처: unknown
타입: document
```

## 🟠 P5. 파일 수정 시 이전 청크가 남음

### 원인

`src/tools/embedding.py:313-321`

```python
new_docs, skipped_count = _filter_new_documents(documents, user_id, source.id)
chunks = _split_documents(new_docs)
if chunks:
    _save_to_chromadb(chunks, user_id)
```

`_filter_new_documents()`(L95)는 **파일 해시가 기존 목록에 없으면 새 문서로 판단**한다.

파일을 수정하면 해시가 바뀌므로 새 문서로 분류되어 추가된다.
그러나 **같은 `file_path`의 이전 해시 청크를 삭제하는 코드가 없다.**

`_delete_source_embeddings()`(L52)가 존재하지만 소스 전체 삭제 시에만 호출되며, 증분 동기화 경로에서는 호출되지 않는다.

### 상태

현재 DB를 검사한 결과 동일 `file_path`에 서로 다른 `file_hash`를 가진 청크는 없다.
**아직 재동기화를 수행하지 않은 상태**이므로 미발현이다.

동기화를 반복하면 수정된 문서마다 구버전 청크가 누적되고, 검색 시 오래된 내용이 최신 내용과 함께 반환된다.

## 🟠 P6. 생성된 일지가 다시 임베딩되지 않음

`src/tools/log.py:91-112` 의 `maker_logfile()` 은 일지를 `logs/YYYY.MM.DD_log.md` 파일로 저장하기만 한다.
저장된 일지를 벡터DB에 다시 넣는 경로가 없다.

프로젝트가 지향하는 계층 구조는 다음과 같다:

```
원문(문서/커밋/대화)  →  그날의 일지  →  위키 / 온톨로지 노드
```

현재는 첫 화살표까지만 존재하고, **일지가 다시 검색 대상이 되지 않는다.**
따라서 "지금까지 한 게 뭐야?" 처럼 여러 날에 걸친 질문에 답하려면 매번 원문 청크를 훑어야 하며, 요약 계층의 이점을 전혀 얻지 못한다.

## 🎯 해결 방향

### 1단계 — 수집 필터 도입 (P1)

- 확장자 화이트리스트를 문서 형식으로 축소: `.md`, `.txt`
- 제외 디렉토리 목록 추가: `.obsidian`, `.git`, `node_modules`, `.venv`, `dist`, `build`, `__pycache__`
- 파일 크기 상한 도입 (기준값 미정)
- 선택 옵션: 소스 등록 시 하위 경로 지정 (예: `Today I Learn/`, `회고록/`)
  → 한 저장소에 여러 프로젝트가 섞여 있는 경우에 대응

### 2단계 — 날짜 추출 (P2)

우선순위를 두고 순차 시도한다:

1. 파일명에서 파싱 (`2026_05_14.md`, `2026-05-14.md` 등)
2. 마크다운 frontmatter의 `date:` 필드
3. Git 커밋 날짜 (`git log -1 --format=%ad -- <file>`) — git 소스에서 항상 사용 가능
4. 파일 mtime — 로컬 소스 최후 수단 (복사/이동 시 부정확)

메타데이터에 `date` 키를 `YYYY-MM-DD` 형식으로 통일해 기록한다.
`_collect_git_log()` 의 `date` 값도 동일 형식으로 정규화한다.

**날짜를 끝내 추출할 수 없는 파일은 수집에서 제외한다.** 일지 시스템의 대상이 아니기 때문이며, 이 규칙 자체가 P1의 보조 필터로도 기능한다.

### 3단계 — 검색 정정 (P3, P4)

- `log.py` 의 필터 키를 실제 기록되는 키에 맞춘다
- 출력부의 `source` / `type` 을 `source_name` / `source_type` 으로 정정
- 날짜 필터 실패 시 무의미한 유사도 폴백 대신, **실패를 명시적으로 반환**한다
- 날짜 범위 조회 지원 검토 (단일 날짜 완전일치는 활용도가 낮음)

### 4단계 — 증분 동기화 정정 (P5)

문서를 저장하기 전에 동일 `file_path`의 기존 청크를 삭제한다 (delete-then-insert).

### 5단계 — 일지 재임베딩 (P6)

`maker_logfile()` 이 파일 저장 후 해당 일지를 `date` 메타데이터와 함께 벡터DB에 등록하도록 한다.
이후 위키/온톨로지 계층의 진입점이 된다.

## ❓ 남은 미결정 사항

**AI 대화 로그 처리 방식** (`_collect_chatlog` 는 여전히 빈 구현)

실측 기준 `~/.claude/projects` 는 79세션에 52MB이며, 세션당 약 660KB다.
문서·Git 소스는 연간 수십 MB 수준이라 부담이 없으나, 대화 로그는 **볼륨이 문제가 되는 유일한 소스**다.

두 가지가 함께 정해져야 한다.

1. **무엇을 넣을 것인가**
   - 세션 원문 전체 — 충실하지만 툴 호출·파일 덤프가 대부분이라 잡음이 크다
   - 사람 발화 + AI 최종 답변만 — `.jsonl` 파싱으로 자동 필터링. 약 1/10로 축소되고 신호 밀도가 높다
   - 세션당 요약 1개 — 일지 계층과 바로 붙지만 세부 추적은 불가

2. **얼마나 오래 보관할 것인가**
   - 전량 영구 임베딩
   - **hot window** — 최근 N일만 벡터DB에 유지하고, 지난 기록은 원문 파일 + 포인터만 남긴다. 일지가 이미 요약 계층 역할을 하므로 과거 원문 청크의 효용이 낮다는 판단에 기반한다

날짜 추출은 세션 파일의 타임스탬프로 해결되므로 이 부분은 추가 설계가 필요 없다.

## 📐 배경: 저장 계층에 대한 판단

논의 과정에서 정리된 전제를 기록해 둔다.

```
원문(문서/커밋/대화)  →  그날의 일지  →  위키 / 온톨로지 노드
   수백 MB               하루 몇 KB        개념 단위
```

**"전부 저장할 것인가, 매번 재임베딩할 것인가"는 잘못된 이분법이다.**
일지 자체가 압축 계층이므로, 계층별로 보관 수명을 다르게 주는 것이 답이다.

- 일지 / 위키 노드 → 영구 임베딩. 검색의 주 진입점
- 문서 / Git 로그 → 영구 임베딩. 연간 수십 MB로 부담이 없음
- AI 대화 원문 → hot window 후보. 지나면 벡터는 버리고 원문 + 포인터만 유지

이번 작업으로 앞의 두 계층은 정상화되었다. 세 번째는 위 미결정 사항에서 다룬다.
