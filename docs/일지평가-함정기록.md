## 📋 이 문서의 성격

일지 생성 기준과 자동 평가를 만드는 과정에서 **잘못된 결론에 도달했다가 되돌린 지점**을
모았다. 결과가 아니라 실패를 남기는 이유는, 같은 함정이 다음에도 그대로 놓여 있기 때문이다.

**아홉 개 중 다섯 개는 잘못된 결론을 실제로 내렸다가 뒤집은 것**이고, 그중 셋은 원인이
같았다 — *다 보지 않고 판단했다*.

| # | 함정 | 잘못된 결론을 냈나 |
|---|---|---|
| 1 | 기준 없이 평가부터 만듦 | — |
| 2 | 요약을 "많이 담았는가"로 측정 | ✅ |
| 3 | 원자료를 잘라 읽고 환각이라 판정 (2회) | ✅ |
| 4 | 분모가 0이라 자동 만점 | ✅ |
| 5 | LLM 채점자의 비재현성 | — |
| 6 | 길이만 점수화한 비대칭 | ✅ |
| 7 | 이름만 나열하면 검색이 약해짐 | — |
| 8 | 개념 노트 층을 성급히 설계 | ✅ |
| 9 | LLM이 LLM을 부르는 우회 | — |

## 1. 기준 없이 평가부터 만들었다

**증상.** 프롬프트에 담을 것을 정하는 문장이 사실상 한 줄뿐이었다.

```
## 배운 것 — 핵심 개념을 항목별로. 자료에 나온 용어를 사용
```

**"핵심"이 무엇인지는 어디에도 정의되어 있지 않았다.** 그런데도 평가 코드는 이미 존재했다.
무엇이 정답인지 정하지 않은 채 채점표부터 만든 셈이다.

**결과.** 모델과 사람이 각자 다르게 판단했고, 그 차이를 "누락"이라고 점수 매겼다.
기준 없이.

**해결.** 기준을 시스템의 목적에서 도출했다. 이 시스템이 답할 세 질문
(*내일 뭘 해야 하나 / 지금까지 뭘 했나 / 전에 그게 뭐였나*)에서 담을 것이 그대로 나온다.

| 담는 것 | 어느 질문에 답하나 |
|---|---|
| 한 일 | 지금까지 뭘 했나 |
| 막힌 것 | 내일 뭘 해야 하나 |
| 정한 것 | 지금까지 뭘 했나 |
| 예정 | 내일 뭘 해야 하나 |
| 다룬 주제 | 전에 그게 뭐였나 |

**교훈.** 평가 지표는 기준의 함수다. 기준이 없으면 지표는 측정하는 것처럼 보이는
임의의 숫자다.

## 2. 요약을 "많이 담았는가"로 측정했다

**증상.** 사람이 쓴 기준 일지를 정답으로 두고 용어 겹침을 커버리지로 계산했다.
많이 겹칠수록 높은 점수.

**문제.** 좋은 요약은 버려야 할 것을 버린다. 그런데 용어 겹침으로 재면 **버릴수록
점수가 떨어진다.** 지표가 요약의 본질과 정반대 방향을 가리킨다.

| 원자료 항목 | 요약에 필요한가 | 지표는? |
|---|---|---|
| 어텐션 수식을 손으로 계산함 | 필요 | 담으면 가점 ✅ |
| "??? 헛점, 전개가 매끄럽지 않다" | 필요 | 담으면 가점 ✅ |
| 비디오 메모리 16GB → 32GB, 48GB, 64GB | **불필요** | **버리면 감점** ❌ |
| ngrok 링크 | **불필요** | **버리면 감점** ❌ |

**한 날짜를 뜯어 보니 왜곡이 양방향이었다.**

| 지표 | 표시값 | 왜곡 | 이유 |
|---|---|---|---|
| 커버리지 | 22.3% | 실제보다 **낮음** | 기준 일지 용어 188개 중 48개가 작성자의 문체 ("살펴봤다", "이어졌다") |
| 근거성 | 76.8% | 실제보다 **높음** | "지어낸 용어" 23개 중 20개가 일반 명사 ("개념", "기반", "주요"). 진짜 환각은 3개 |

**해결.** 비교 대상을 사람이 쓴 일지에서 **원자료**로 바꿨다. 기준 문서가 "반드시
담으라"고 정한 것만 원자료에서 찾아 확인한다. 문체가 분모에 섞이지 않는다.

**부수 효과.** 정답 일지가 필요 없어졌다. 사람이 손으로 쓴 5일이 아니라 55일 전부를
평가할 수 있게 되었다.

## 3. 원자료를 잘라 읽고 환각이라 판정했다 — 두 번

**증상.** 모델이 쓴 일지를 읽고 "이건 원자료에 없다, 환각이다"라고 판정했다.
**두 번 다 틀렸다.**

| | 내가 읽은 양 | 실제 원자료 | 환각이라 지목한 것 |
|---|---|---|---|
| 2026-06-15 | 700자 | **4,105자** | `neo4j`, `jena`, `hnsw`, `chroma`, `원핫`, `crud`, `retriever`, `복습 주기`, `연역/귀납`, `pdf` |
| 2026-07-27 | 600자 | **4,475자** | `Next.js`, `LangGraph`, `FBL`, `prefill/decode/autoregression`, `Flash Attention` |

**전부 원자료에 있었다.** 4,000자짜리 자료에서 600자만 읽고 "없다"고 단정했다.

실제로 근거가 없었던 것은 06-15의 `300차원`, 07-27의 `온프레미스` 정도였다.

**원인.** 원자료를 화면에 띄울 때 앞부분만 잘랐다. 사람은 긴 자료를 끝까지 읽지 않는다.

**교훈.** **자동 평가가 필요한 이유는 "빠르니까"가 아니라 "사람보다 정확하니까"다.**
코드는 4,475자를 전부 확인한다. 지치지도, 앞부분만 보고 넘어가지도 않는다.

## 4. 분모가 0이라 자동 만점이 나왔다

**증상.** 「막힌 것 포착」이 94~98%로 높게 나왔다. 좋아 보였다.

**실체.** 분모를 정규식으로 셌다.

```python
_BLOCKER = re.compile(r"\?{2,}|헛점|허점|매끄럽지|모르겠|불명확|헷갈")
```

`???`나 "헛점" 같은 **표시가 붙은 것만** 센다. 그 결과:

```
분모 0개 → 43일 (78%)
분모 1개 →  8일
분모 2개 →  2일
분모 3개 →  2일
```

분모가 0이면 코드가 자동으로 100점을 준다 (`if blockers else 1.0`). 잡을 것이 없으니
놓친 것도 없다는 논리다. **높은 점수의 대부분이 여기서 나왔다.**

**낸 잘못된 결론.** 세 모델 격차가 3.7%p로 나오자 "품질 차이가 거의 없다,
Haiku로 충분하다"고 판단했다. 실행에 옮기기 쉬운 형태의 결론이라 더 위험했다.

**실체.** 분모를 300개로 바로잡자 격차가 **15.4%p**로 벌어졌다. 차이가 없었던 게
아니라 **자가 차이를 못 재고 있었다.**

| | 정규식 분모 | 고정 풀 분모 |
|---|---|---|
| 분모 합계 | 12개 | **300개** |
| 같은 Haiku 일지 점수 | 96% | **58%** |

38%p가 측정 착시였다.

**교훈.** 점수가 높으면 먼저 분모를 의심한다. "잘해서 100점"과 "잴 게 없어서 100점"은
구분되지 않는다.

## 5. LLM에게 매번 물으면 재현되지 않는다

**증상.** 정규식 대신 LLM에게 분모를 물으면 정확해진다. 그런데 같은 자료·같은 프롬프트·
같은 모델로 세 번 돌린 결과가 이랬다.

| 실행 | 항목 수 | 실행별로만 나온 항목 |
|---|---|---|
| 1회차 | 8개 | 프로덕션 레벨 모델 서빙 준비 |
| 2회차 | **10개** | LangChain 마이그레이션 미완료, FastAPI 배포 미완료, 하이브리드 DB 미완료 |
| 3회차 | **6개** | 코드 검증 기준 모호함 |

**같은 일지가 5개를 잡았을 때** 분모 6이면 83%, 분모 10이면 50%다.
**33%p 차이가 순전히 채점자의 변덕에서 나온다.**

이러면:
- 프롬프트 개선이 진짜인지 노이즈인지 구분할 수 없다
- 모델 간 3.7%p 차이는 아무 의미가 없다
- "이번 변경으로 나빠졌다"를 판정할 수 없다

**temperature로 해결되지 않는다.** Sonnet 5와 Opus 5는 `temperature` 파라미터가
제거되어 보내면 400 에러다. **최신 모델에서는 결정론을 요청할 수단조차 없다.**

**해결 — 풀링(pooling).** 정보검색 평가에서 쓰는 방식이다. 분모를 한 번 만들어
파일로 고정하고, 채점은 그 파일을 읽는다.

```
세 모델이 각자 추출  →  합집합  →  중복 병합  →  <date>.blockers.json  →  고정
                                                      ↑
                                         이후 채점은 이 파일만 읽음 (비용 0)
```

**여러 모델을 쓰는 이유.** 한 모델이 만든 목록으로 채점하면 그 모델의 관점이 곧 정답이
되어 자기 자신에게 유리해진다. TREC 풀링이 참가한 모든 시스템의 결과를 모아 풀을
만드는 것과 같은 이유다.

> 후발 시스템은 상위 결과 중 상당수가 미판정으로 남아, **실제로는 더 효과적일 수 있는
> 접근을 오히려 벌하게 된다** — [Pooling-based continuous evaluation of IR systems](https://link.springer.com/article/10.1007/s10791-015-9266-y)

**병합 임계값은 실측으로 정했다.**

| 쌍 | 유사도 | 합쳐야 하나 |
|---|---|---|
| "느린 코랩" ↔ "코랩이 느려서 불편함" | 0.770 | 예 |
| "왜 이렇게 복잡하지?" ↔ "이미 다 한 걸 왜 복잡하게 하나" | 0.638 | 예 |
| "랭체인 없이도…" ↔ "랭그래프 없이도…" | 0.802 | 예 |
| "새로운 개념 쏟아짐" ↔ "성과의 정량 지표화" | 0.117 | 아니오 |
| "느린 코랩" ↔ "코드 검증 근거?" | 0.275 | 아니오 |

합쳐야 할 쌍(0.638~0.802)과 아닌 쌍(0.117~0.275) 사이가 넓게 비어 있어 **0.60**으로 정했다.
처음 잡았던 0.82는 너무 높아 명백히 같은 항목이 갈라졌다.

**남은 결함.** 0.60도 긴 문장에서는 실패한다. `느린 코랩`과 `코랩이 느려서 한 페이지에
작성해야 했음`이 갈라져 두 항목으로 남았고, **둘 다 잡은 Opus가 점수를 두 번 받았다.**
임계값을 더 낮추면 오합침이 생기므로, 항목을 짧은 구절로 정규화한 뒤 비교해야 한다.

## 6. 길이만 점수화해 비대칭이 생겼다

**증상.** 프롬프트에 "대개 500자 안쪽이면 충분하다"고 명시했으나 세 모델 모두 초과했다
(567 / 618 / 890자). Opus가 57% 초과해 간결성 점수에서 크게 감점됐다.

**낸 잘못된 결론.** "능력이 높은 모델이 오히려 기준을 덜 지켰다."

**실체 — 두 가지가 겹쳤다.**

### 6-1. 길이 제약은 애초에 지킬 수 없는 지시였다

> GPT-4 같은 최첨단 LLM조차 길이 제약을 정확히 따르지 못한다. **500단어 이내로
> 요청해도 초과하는 경우가 잦다** — [Following Length Constraints in Instructions](https://arxiv.org/pdf/2406.17744)

> 현재 LLM은 길이 지시를 따르는 데 광범위한 어려움을 보이며, **긴 길이 제약에서
> 특히 심하다** — [LIFEBench](https://arxiv.org/pdf/2505.16234)

원인은 **토크나이저가 단어가 아니라 토큰 단위로 동작해 모델이 글자 수를 정확히
인지하지 못하고, 학습 데이터에 엄격한 길이 제약 예시가 드물다**는 것이다.

### 6-2. 측정 가능한 것만 벌하는 구조였다

```
Opus가 더 잡아냈다  →  분모(정규식 12개)에 없는 항목이면 점수 반영 안 됨
Opus가 더 길어졌다  →  길이는 정확히 측정되어 감점
```

**추가 회수는 측정되지 않고 추가 분량만 측정되었다.** 이것이 "세 모델 품질 차이 없음,
Opus만 분량 초과"라는 결론을 만들었다.

실제로는 같은 자료(2026-06-22)에서 Opus가 「막힌 것」 6개를 찾을 때 Haiku는 2개만
찾았다. Opus만 잡은 것들:

```
- 성과와 실력의 객관적 정량 지표화 — "우리 모두의 숙원"
- 코드를 검증하는 근거(기준)는 무엇인가 → 기술적 < 비즈니스
- 코랩이 느림 → 한 페이지에 작성으로 대응
- 세션의 한계: 단기 메모리 DB 저장 필요
```

**해결.** 프롬프트에서 "500자 안쪽" 문구를 삭제하고, `concise` 지표를 점수 없는
참고값(`score: None`)으로 바꿨다.

**참고 — 흔한 편향은 반대 방향이다.** LLM-as-Judge 연구에서 알려진 것은 **긴 답변을
선호**하는 verbosity bias다.

> 모델별로 다르다: Pro/Llama/Flash는 전형적 verbosity bias(긴 것 선호, +0.24~+0.44),
> **Claude는 반대로 짧은 것 선호(−0.12)**, GPT-4o는 중립 —
> [Evaluating and Mitigating LLM-as-a-judge Bias](https://arxiv.org/html/2510.12462v1)

우리 지표는 `concise = min(1.0, 500/length)`로 짧은 것을 선호하도록 **직접 박아 넣었다.**
흔한 편향은 피했지만 반대편으로 기울었다.

## 7. 이름만 나열하면 검색이 약해진다

**배경.** 원문 검색이 절반만 동작한다는 것을 먼저 확인했다.

| 검색어 | 1위 결과 | 판정 |
|---|---|---|
| 야코비 행렬 | `2026-06-13` 원문 — 정확 | 성공 |
| 동치관계 조건 | `2026-05-23` AI 대화 — 한국어 문장 | 성공 |
| **코시 수열** | `2026-06-05` CNN 역전파 수식 | **실패** |

`코시 수열`은 실제로 `2026-06-13` 원문에 있는데 찾지 못했다. 그 청크가
`\begin{gather*}` 범벅인 LaTeX 덩어리라 한국어 신호가 거의 없고, 대신 다른 날의
수식 덩어리끼리 서로 가까워졌기 때문이다.

**그래서 일지가 다리 역할을 한다.** 일지는 깨끗한 한국어라 검색에 잘 걸리고, 날짜를
알아내면 `date` 필터로 그날 원문 전체를 정확히 가져올 수 있다. **퍼지 검색은 1단계에서
한 번만 쓰고, 그 뒤로는 정확한 키로 넘어간다.**

**함정.** 일지에 개념 **이름만** 나열하면 그 다리가 약해진다.

| 질의 | 이름만 나열 | 이름 + 한 줄 |
|---|---|---|
| 코시 수열 | 0.3888 | **0.5231** (+34%) |
| 코시 수열이 뭐였지 | 0.3527 | **0.4814** (+36%) |
| 야코비 행렬 | **0.2445** | 0.2327 (−5%) |

**중심점 문제다.** 이름 18개를 나열하면 벡터가 그 18개의 **평균 위치**로 가는데,
평균은 어느 개념과도 멀다. 한 줄 설명이 붙으면 벡터가 그 개념 쪽으로 당겨진다.

마지막 행이 한계를 보여준다 — 목록이 길어질수록 각 항목의 신호가 희석되어,
한 줄을 붙여도 효과가 사라진다.

**현재 결정.** 이름만 쓴다. 개념 검색은 원문이 담당하고, 일지는 "그날 무슨 주제를
다뤘나"만 표시한다. 개념 검색을 일지가 책임지게 하려면 별도의 개념 노트 층이
필요한데, 그것은 8번에서 보듯 아직 이르다.

---

## 8. 개념 노트 층을 성급히 설계했다

**제안했던 것.** 일지의 「배운 것」을 항목별로 쪼개 각각 하나의 청크로 임베딩하자.

**사용자의 반박.** 그러면 일정 관리용 벡터DB와 지식용 벡터DB가 사실상 분리되는 셈
아닌가? 청크를 그렇게 많이 나눠도 괜찮은가?

**반박이 옳았다.** 날짜별 일지 안에서 개념을 쪼개면 **같은 개념이 날짜마다 흩어진다.**
코시 수열이 6월 13일에도 6월 15일에도 나오면 청크가 둘 생기는데, 둘은 서로 모른다.
"코시 수열에 대해 내가 아는 것"이 한곳에 모이지 않는다.

**수정한 설계.** 층을 하나 더 둔다.

```
원문        날짜별 · 있는 그대로
  ↓
일지        날짜별 · 그날의 서사
  ↓
개념 노트   개념별 · 날짜 무관 (여러 날의 언급이 한 노트에 누적)
```

**그런데 지금은 만들 수 없다.** 후보 용어를 세어 보니:

```
전체 고유 용어  6,479개  (55일)
  2일 이상 등장  2,054개
  3일 이상 등장  1,159개
```

빈도 상위는 이렇다.

```
52일  피드백      ← 개념이 아님 (매일 있는 일정)
51일  https       ← 노이즈
31일  프로젝트     ← 너무 일반적
24일  fastapi     ← 이건 개념
23일  llm         ← 이것도
18일  github.com  ← 노이즈
```

**빈도로는 개념을 못 고른다.** 결국 LLM 판단이 필요한데, 그 전에 아래층인 일지 기준부터
확정하는 것이 순서다. 개념 노트 층은 일지가 쌓인 다음 문제로 미뤘다.

**교훈.** 아래층이 확정되기 전에 위층을 설계하면, 위층의 요구가 아래층의 기준을
왜곡한다. 실제로 이 논의 때문에 "일지를 항목별로 쪼개자"는 잘못된 방향으로 갈 뻔했다.

## 9. LLM이 LLM을 부르는 우회를 만들었다

**증상.** 테스트용 더미 데이터(커밋 이력, AI 대화)를 만들기 위해 스크립트를 짜고,
그 스크립트가 API를 호출해 Sonnet에게 생성을 시켰다.

**사용자의 지적.** *"더미데이터를 만드는데 코드를 쓸 필요가 있어? 그냥 폴더에 넣으면
되는 거잖아"*

**옳은 지적이었다.** 나 자신이 LLM인데 API로 다른 LLM을 불러 같은 일을 시켰다.
파일을 직접 쓰면 될 일에 별도 비용이 들었다.

**비슷한 낭비가 한 번 더 있었다.** 분모를 고친 뒤 세 모델을 재채점하려고 55일 × 3모델 =
**165회 호출로 일지를 다시 생성**하려 했다. 일지는 이미 LangSmith에 저장되어 있었으므로,
그것을 끌어와 채점만 하면 되는 일이었다. 사용자가 *"일지를 새로 뽑을 필요 없는데
오래걸리네?"* 라고 지적해 중단했다.

**교훈.** 재생성과 재채점을 구분한다. 평가 지표가 바뀌었을 때 필요한 것은
**채점만 다시 하는 것**이지 생성물을 다시 만드는 것이 아니다. 생성물과 채점을 분리해
저장해 두면 이 실수를 구조적으로 막을 수 있다 — 그래서 `<date>.sources.json`에
채점 근거를 함께 남긴다.

## 정리 — 반복된 패턴

아홉 개 중 셋(2, 3, 4)은 **원인이 같다.**

| # | 무엇을 다 보지 않았나 |
|---|---|
| 2 | 지표가 무엇을 세는지 — 분모에 문체가 섞인 것을 보지 않음 |
| 3 | 원자료 — 4,000자 중 600자만 읽음 |
| 4 | 분모 분포 — 43일이 0이라는 것을 보지 않음 |

**전부 "다 보지 않고 판단했다"다.** 그리고 셋 다 실행에 옮기기 쉬운 결론
("환각이다", "모델 차이가 없다")으로 이어졌다는 점에서 위험했다.

측정 도구를 만들 때 가장 먼저 확인할 것은 **분모가 무엇이고 그것이 타당한가**다.
